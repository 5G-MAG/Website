<h1>Test design</h1>

:::tip[At a glance]

- **Scenarios:** eleven AI interaction patterns, from chat to agent-to-agent collaboration, each with its call flow.
- **Network profiles:** ten deployment conditions, from an ideal baseline and a 6G HRLLC profile to satellite and congested links, plus a lossy profile to find where a scenario breaks.
- **A test run:** one scenario, one profile and one execution mode, repeated; the output is a metric record.
- **Source:** TR 26.870 V0.6.1 annexes B to E, a draft.

:::

## Scenarios

| Scenario | Providers | What it exercises | Clause |
| --- | --- | --- | :---: |
| Chat (streaming, non-streaming, tokens) | OpenAI, Gemini, DeepSeek, Qwen | Single- or multi-turn text chat. Streaming responses arrive as Server-Sent Events. In the tokens variant the client sends token identifiers from a local tokenizer as the prompt. | D.1.2.1 |
| Agent with MCP | OpenAI, DeepSeek | An agentic loop: the model calls tools (web search, browser) through MCP until it reaches a final answer. Captures tool latency and loop factor. | D.1.2.2 |
| Image generation | OpenAI | An image generation request, measuring request size, response size and generation latency | D.1.2.3 |
| Multimodal analysis | OpenAI, Gemini, llama.cpp | An image or document with a text prompt, measuring upload bytes, response bytes and latency | D.1.2.4 |
| Multimodal analysis, live AI mode | llama.cpp | The client periodically uploads an image to a file server and sends a streaming request with its URL | D.1.2.12 |
| Video understanding | Gemini, vLLM; Qwen (non-real-time), Liquid (real-time) | Real-time: a WebRTC session whose video track carries video tokens to the server and whose data channel carries the prompt and the streamed result. Non-real-time: one request with the video and a text prompt. | D.1.2.5 |
| Real-time text and audio | OpenAI | A persistent bidirectional connection, WebSocket for text and WebRTC for audio, measuring per-event timing, TTFT, TTLT and audio bytes | D.1.2.6 |
| Direct web search | OpenAI, DeepSeek | Multi-threaded direct web search without MCP, optionally synthesised by the model | D.1.2.7 |
| Computer use | OpenAI | A browser-automation agent: each step sends a screenshot to the model and performs the action returned, measuring screenshot bytes, action count and action latency | D.1.2.8 |
| Personal assistant agent | A local agent runtime with a commercial or local model | A self-hosted agent on the user device. The local control channel and the runtime egress to the model and tools are measured separately, as the network would see them. | D.1.2.9 |
| Agent-to-agent collaboration (single task, streaming, multi-agent) | Deterministic test agents, local or remote | Capability discovery, delegation and result exchange over an HTTP-based agent protocol. The agents contain no model, so the cost measured is that of the protocol and its transport. | D.1.2.10 |

The AI gateway scenario (clause D.1.2.11) places an intermediary between AI applications and model providers, which authenticates, routes, applies policies and optionally enriches the prompt. Its test definition is still to be provided.

The call flows TR 26.870 gives for the scenarios, between the client the testbed drives, the client library and the model or service.

## Network profiles

The recommended profile set (TR 26.870 table D.3.1-1). The profiles other than the lossy profile represent deployment conditions, so their loss rates are low. The lossy profile is applied at a range of loss rates to find the boundary of the region in which a scenario works; results with it characterise resilience and are not expected operating conditions.

| Profile | Delay | Jitter | Loss | Rate | Role |
| --- | --- | --- | --- | --- | --- |
| ideal | none | none | none | none | Clean baseline for all scenarios |
| 6g_itu_hrllc | 1 ms | | 0.001 % | 300 Mbit/s | Derived from the HRLLC profile of ITU-R M.2160 (IMT-2030); buffer of 2000 packets |
| 5g_urban | 20 ms | 5 ms | 0.1 % | 100 Mbit/s | Representative mobile broadband |
| wifi_good | 30 ms | 10 ms | 0.1 % | 50 Mbit/s | Non-cellular access comparison point; a fictional average of common Wi-Fi configurations |
| cell_edge | 120 ms | 30 ms | 1.0 % | 5 Mbit/s | Poor coverage, unstable edge of cell; heavier-tailed jitter, burst loss, small reorder rate |
| satellite_leo | 22 ms | 7 ms DL, 8 ms UL | 0.5 % DL, 0.8 % UL | 100 Mbit/s DL, 15 Mbit/s UL | Remote access and NTN-like latency stress |
| satellite_geo | 340 ms | 15 ms DL, 18 ms UL | 0.1 % DL, 0.2 % UL | 50 Mbit/s DL, 3 Mbit/s UL | Defined from published satellite measurement reports |
| congested | 200 ms | 50 ms | 3.0 % | 1 Mbit/s | Severe bottleneck; heavier-tailed jitter, burst loss, queue limit, small reorder rate |
| 5qi_7 | 80 ms | 10 ms | 0.1 % | uncapped | 5QI anchor for live streaming and interactive traffic |
| 5qi_80 | 8 ms | low, non-zero | 0.0001 % | uncapped | 5QI anchor for low-latency eMBB and AR-like traffic |
| lossy | none | none | 1 % to 30 % (uplink) | none | Loss tolerance of a scenario, isolated from delay |

The TR notes that this is an initial set based on information available in SA4, and that the 3GPP averaging window and resource type are not taken into account. For satellite_leo, the same table cell also gives 100 ms delay, 20 ms jitter, 0.3 % loss and 4 Mbit/s before defining the separate downlink and uplink parameters shown here.

## How a test runs

A test run takes a scenario, a network profile and an execution mode, and produces a metric record; several runs are executed for each combination. The two execution modes differ in where the model runs:

- **Remote execution:** at a public cloud provider. Traffic crosses the main network interface, where it is captured and impaired.
- **Local execution:** a self-hosted model on a server next to the client. Traffic crosses the loopback interface, emulating a radio link to a local edge server.

<details>
<summary>The parts of the testbed</summary>

The testbed builds on the common test platform of TR 26.934, which provides an end-to-end framework to run scenarios, emulate network conditions and log metrics reproducibly. Its architecture is orchestrator-centric, with scenarios, clients, network emulation, capture and analysis kept separate:

| Part | Role |
| --- | --- |
| `orchestrator.py` | Coordinates scenario runs, applies network profiles, handles retries and generates reports |
| `scenarios/` | Implements the traffic patterns: chat, agent, direct search, real-time, multimodal, image, video, computer use, personal assistant agent, agent-to-agent collaboration |
| `clients/` | Provider adapters, including OpenAI, Gemini, DeepSeek (OpenAI-compatible) and vLLM for self-hosted models |
| netem | The network emulator, an external dependency proposed to be common to all studies |
| `capture/` | L3/L4 packet capture (PCAP) and L7 capture through mitmproxy |
| `analysis/` | Logs to SQLite, computes the metrics and generates plots |

Trace logging gives visibility into protocol and payload behaviour, for example WebRTC SDP samples and the exact request and response payloads of an agent.

</details>

<details>
<summary>The method in full</summary>

TR 26.870 sets out an initial methodology; other methodologies are not precluded.

1. The AI traffic use cases of TR 22.870 are categorised against the scenarios, to check that the scenarios are meaningful in a 6G context.
2. A set of representative scenarios implements the use cases. A scenario is a named, reproducible AI interaction pattern, defined by its input and output modalities, its interaction style (real-time or batch, streaming or not), its protocol and its AI model or provider.
3. Metrics are defined as computable scalar quantities from which traffic characteristics can be stated.
4. Network profiles emulate real-world access technologies, together with stress-test profiles.
5. Two execution modes are distinguished, by where the model weights are loaded and the forward pass is computed:
   - **Remote execution:** the inference engine is hosted by a public cloud provider, beyond the testbed's control. Traffic crosses the main network interface, where it is captured and impaired.
   - **Local execution:** the inference engine is a self-hosted model on a server co-located with the client. Traffic crosses the loopback interface, where it is captured and impaired, emulating a radio link to a local edge server.

A test run takes a scenario, a network profile and an execution mode, and produces a metric record. Several runs are executed for each combination.

The TR also lists, in brackets, principles still under discussion: metrics reported only per scenario and profile, never aggregated across scenarios without labelling; raw traces shared selectively for independent verification; results at three levels (per run, per cell, cross-cell summary); repetitions for robust percentiles; and independent collation by several companies.

</details>

<details>
<summary>The network emulator</summary>

The network emulator, netemu, is a Python wrapper around the Linux tc toolchain that depends only on the Python standard library and a YAML parser. It covers four independent stages of a measurement run:

- **Emulation:** tc, netem and HTB impose the impairments on egress and, through an IFB device, on ingress.
- **Capture:** tcpdump on the shaped interface, with a metadata file alongside each capture.
- **Analysis:** a capture is parsed into per-packet records, per-flow records and per-capture aggregates. Direction is derived from the TCP handshake, not from port numbers. Per-flow metrics are computed for TCP only; for QUIC, only metrics from packet sizes, timestamps and directions.
- **Aggregation:** one or many parsed captures are summarised into distributions.

A profile sets one-way delay and jitter, the delay distribution (normal, pareto, paretonormal or fixed) and correlation, loss and its correlation or a Gilbert-Elliott loss model, an HTB rate ceiling and burst sizes, corruption, reordering and duplication rates, and the transmit queue length.

</details>
