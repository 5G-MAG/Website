export const part = (keys, profile) => {
  const features = AUDIT.features
    .map((f) => ({ ...f, summary: profile ? ((SUMMARY[profile] || {})[f.name] || '') : f.summary,
                   requirements: f.requirements.filter((r) => keys.includes(r.release)) }))
    .filter((f) => f.requirements.length);
  const pick = (o) => Object.fromEntries(Object.entries(o).filter(([k]) => keys.includes(k)));
  return { ...AUDIT, features, releases: pick(AUDIT.releases), releaseNames: pick(AUDIT.releaseNames || {}) };
};

export const count = (data, rel, inherit) => {
  let reqs = data.features.flatMap((f) => f.requirements);
  if (inherit) reqs = reqs.concat(UNPROFILED.features.flatMap((f) => f.requirements).filter((r) => !NOT_IN[inherit].includes(r.id)));
  const cases = reqs.flatMap((r) => r.cases).map((c) => (rel && c.byRelease && c.byRelease[rel] ? { ...c, ...c.byRelease[rel] } : c));
  const n = (v) => cases.filter((c) => c.verdict === v).length;
  return { reqs: reqs.length, cases: cases.length, implemented: n('implemented'), differs: n('differs'), absent: n('absent'), inconsistent: n('inconsistent') };
};

:::tip[In short]

- **rt-libflute** is a FLUTE sender and receiver. It is judged against every requirement of the FLUTE documents that falls on a sender or a receiver, in each of the four ways FLUTE is specified:
  - **[Unprofiled FLUTE](#unprofiled-flute)** (RFC 3926 and its building blocks): {CU.reqs} requirements in {CU.cases} cases: {tally(CU)}.
  - **[FLUTE version 2](#flute-version-2)** (RFC 6726): {CV2.cases} cases: {tally(CV2)}.
  - **[MBMS download](#mbms-download)** (TS 26.346, with the unprofiled requirements it keeps): {CM.cases} cases: {tally(CM)}.
  - **[MBS Object Distribution](#mbs-object-distribution)** (TS 26.517 and the MBMS Download Profile, with the unprofiled requirements they keep): {CB.cases} cases: {tally(CB)}.
- **Releases:** the 3GPP profiles are judged at Release 18 (TS 26.346 V18.2.0, TS 26.517 V18.6.0), the issues the code is built against; Release 17 gives the same result. At Release 19 (TS 26.346 V19.3.0, TS 26.517 V19.3.0), MBMS download has {CM19.implemented} of {CM19.cases} cases implemented and MBS Object Distribution {CB19.implemented} of {CB19.cases}: the code writes the Release 18 FDT schema versions, 4 and 2, where Release 19 requires 5 and 3.
- **Not judged here:** session descriptions, reception and operating modes, caching policy and repair belong to the components that use the library: the MBS Client (rt-mbs-client) and the MBSTF (rt-mbs-transport-function) for MBS, the MBMS Client (rt-mbms-client) and the BM-SC (rt-mbms-bmsc) for MBMS; [see below](#judged-with-the-clients-and-the-mbstf).
- **Source of this page:** a code audit of the repository, every open change read as merged: each requirement split into the cases its clauses define, then re-checked by a second reader.

:::

For what the specifications define, see the [Standards page](/standards/content-delivery/flute) and the [Technical Analysis](/tech/content-delivery/features). For how to run the tools, see the [Tutorials](/reference-tools/content-delivery/tutorials).

## Unprofiled FLUTE

FLUTE version 1 as the IETF defines it: RFC 3926 on ALC and LCT, the FEC building block and schemes, and WEBRC congestion control. The 3GPP profiles keep most of these requirements as they are; the sections below give only what they change or add. Filter by component; open a feature, then a requirement.

## Judged with the clients and the MBSTF

rt-libflute is the FLUTE layer of four Reference Tools, one sender and one receiver for each 3GPP profile:

| Profile | Sender | Receiver |
| --- | --- | --- |
| MBMS download | BM-SC (rt-mbms-bmsc) | MBMS Client (rt-mbms-client) |
| MBS Object Distribution | MBSTF ([rt-mbs-transport-function](https://github.com/5G-MAG/rt-mbs-transport-function)) | MBS Client, its MBSTF Client (rt-mbs-client) |

These requirements of the same documents fall on those components rather than on the library:

| Feature | Documents | MBS Object Distribution | MBMS download |
| --- | --- | --- | --- |
| Session description | RFC 3926 section 6; TS 26.346 clause 7.3 and table L.4.8-1; TS 26.517 clause 6.2.2 | MBS Client and MBSTF: [5G MBS implementation](/reference-tools/5g-mbs/implementation) | MBMS Client and BM-SC: not yet audited case by case |
| Reception and operating modes | TS 26.346 clause 7.2.0; TS 26.517 clause 6.2.3 | MBSTF: [5G MBS implementation](/reference-tools/5g-mbs/implementation) | MBMS Client: not yet audited case by case |
| Caching policy | TS 26.346 clause 7.2.13 | MBS Client; the library reads the directives (above) | MBMS Client; the library reads the directives (above) |
| Repair and reception reporting | TS 26.346 clauses 9.3, 9.4 and 9.4B; TS 26.517 clause 6.2.4 | MBS Client: [5G MBS implementation](/reference-tools/5g-mbs/implementation) | MBMS Client: not yet audited case by case |

## rt-media-origin: packaging and delivery

A config-driven media origin: it packages each channel with ffmpeg as DASH, HLS or CMAF, and delivers it over HTTP or a push transport.

| Transport | Document it follows | What the receiving side needs |
| --- | --- | --- |
| `http` | HTTP | A DASH or HLS player |
| `rtsp` | RFC 2326 (RTSP 1.0) | A server that accepts RTSP 1.0 publishing (ANNOUNCE and RECORD), such as MediaMTX; RFC 7826 (RTSP 2.0) removed both |
| `rtmp` | Adobe RTMP 1.0 with FLV 10.1 | For HEVC, VP9, AV1 or VVC, Enhanced RTMP and a server that supports it |
| `srt` | draft-sharabayko-srt-01 (expired) | A Stream ID declaring the mode when publishing to a relay |
| `rist` | VSF TR-06-1:2020 (Simple Profile) | An even media port, RTCP on the next one |
| `rtp` | RFC 2250 over RFC 3550 | A receiver for MPEG-TS over RTP, payload type 33 |
| `moq` | draft-lcurley-moq-lite | A moq-lite relay, such as moq-dev's `moq-relay` |
| `flute` | rt-media-origin API | FLUTE transmission is done by rt-libflute-based tooling; the origin publishes the session metadata |

It checks the manifests it produces against these named profiles. The checks cover manifest and segment signalling and structure, not codec or bitstream conformance.

| Profile | Specification |
| --- | --- |
| DASH-IF | ISO/IEC 23009-1, isoff-live-2011 |
| DVB-DASH | ETSI TS 103 285 |
| 5GMS DASH IOP | TS 26.247 clause 7.3.11 |
| CMAF | ISO/IEC 23009-1, urn:mpeg:dash:profile:cmaf:2019 |
| TV 720p HD | TS 26.116 |
| VR/OMAF Basic | TS 26.118 |
| DASH-IF Low-Latency | DASH-IF IOP v5 |
| HLS | RFC 8216 |

## Coded Multisource Media Format (CMMF)

[rt-cmmf-encoder](https://github.com/5G-MAG/rt-cmmf-encoder) is an early-stage reference implementation of ETSI TS 103 973, packaging content for delivery from more than one network source at once. It is not yet audited against the published standard.
