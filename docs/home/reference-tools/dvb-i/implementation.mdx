## What This Project Implements

This page contains information such as the specifications within the scope of the tools and high-level architectures that bring context to their applicability.

This project provides reference tools for delivering DVB-I (Digital Video Broadcasting - Internet) services over 5G networks. DVB-I defines a common service discovery and selection framework that lets internet-connected devices find and access sets of linear TV services, along with their programme metadata, independently of the underlying access network.

The work focuses on combining DVB-I with 5G delivery so that the same service can reach devices over different paths:

- Unicast delivery using 5G Media Streaming (5GMS)
- Broadcast delivery using the LTE-based 5G Broadcast System
- Concurrent or hybrid delivery over both paths

The DVB / 5G-MAG Joint Task Force documented the reference architecture and deployment guidance for these scenarios in ETSI TR 103 972 (DVB-I service delivery over 5G Systems; Deployment Guidelines).

## Reference tools

The reference tools cover DVB-I service discovery and selection, bootstrap procedures, and integration with both the 5GMS unicast path and the 5G Broadcast path, so that a hybrid broadcast and broadband TV experience can be demonstrated end to end. See [Repositories & Releases](/reference-tools/dvb-i#repositories--releases) on the project index for the available repositories and [Developer Updates](/reference-tools/dvb-i#developer-updates) for planned work.

### How the tools map to the standard

The DVB-I over 5G tools implement the discovery and selection layer and glue it to the transport that 5G-MAG's other reference tools provide:

- **Service discovery and selection** (DVB A177 / ETSI TS 103 770): fetching and parsing a service list, evaluating the service instances on each service, and choosing a delivery instance. This includes the bootstrap flow via a Service List Registry where one is used.
- **Programme metadata**: retrieving and presenting content-guide data for the selected services.
- **Unicast delivery**: handing a DVB-DASH service instance to the 5G Media Streaming client path. The 5GMS behaviour itself lives in the [5G Media Streaming reference tools](../5gms/).
- **Broadcast delivery**: acquiring a broadcast service instance over the LTE-based 5G Broadcast path. The receiver/modem behaviour lives in the [5G Broadcast reference tools](../5g-broadcast/).
- **Concurrent / hybrid operation**: presenting both instances for a service so the client can select or switch between broadcast and unicast.

This mapping mirrors the DVB-I-over-5G reference architecture in ETSI TR 103 972 clause 5.1: DVB-I stays the service layer, DVB-DASH stays the media layer, and the 3GPP/ETSI systems stay the transport layer.

### DVB-I over 5G

ETSI TR 103 972 V1.1.1 (2023-07), *DVB-I service delivery over 5G Systems; Deployment Guidelines*, is an informative technical report: it places no requirement on a DVB-I client, service list provider or registry, so nothing in this section is scored. It describes three scenarios (5G Broadcast, 5G Media Streaming, and both at once) and records the gaps the DVB and 3GPP specifications leave. What the reference tools do towards them:

- **5G Broadcast instances use an existing DVB-I element.** TS 103 770 V1.2.1 clause 9.3.3 acts on "a DVB-I service instance with an mbms:// locator" without naming the element that carries it, and TR 103 972 clause 6.2.4 asks for "an extension" for it. The provider puts the `mbms://` URL in `IdentifierBasedDeliveryParameters`, which table 16 defines as "An identifier in the form of a locator (URL) or name (URN) that contains the parameters of the relevant delivery system for this service instance." No clause names that element for MBMS, so this is a reading, and the "new set of service delivery parameters" the TR also asks for has no home. The list validates against the published schema, and the provider refuses a locator that is not an MBMS URL by ETSI TS 126 347 clause 8.2.2.
- **The registry** says nothing about 5G: TS 103 770 gives it no element or `Delivery` value for it.
- **The client** cannot receive over MBMS from a browser, so it checks the signalling instead: a 5G badge shows the locator, its priority and the MBMS User Service it names, or what is wrong with it. It plays the service from a DASH or HLS instance where one exists.
- **5G Media Streaming:** no component yet carries 5GMS Service Access Information, which TR 103 972 clause 6.3.3.2 says a service list "needs to convey" and clause 6.3.4 lists as a gap. The Exo DVB-I Player hands an intercepted DASH address to ExoPlayer, without a Media Session Handler.

TS 103 770 clause 9.3 (carriage in an MBMS system) is part of the status above, under *Service instance selection and delivery*.
