The [DVB-I Application Provider](https://github.com/5G-MAG/rt-dvb-i-application-provider) publishes a DVB-I service list and its content guide, and gives an admin portal for maintaining them without editing XML. It is the Service List Server and the Content Guide Server of the architecture in ETSI TS 103 770 V1.2.1, clause 4.1. In this tutorial you run it, add a channel, publish the list and the programme guide of that channel, and check what it publishes against the DVB-I schema.

:::tip[Read the READMEs first]
Read the README of [rt-dvb-i-application-provider](https://github.com/5G-MAG/rt-dvb-i-application-provider#readme) before you start; it points to `DEPLOYMENT.md` for the settings you need before anyone else can reach the server. The other repositories below are only needed in the sections that name them.
:::

**You need:** a Linux machine with `git`, Node.js 20 or later with `npm`, `curl` and a browser; about 30 MB of disk. For section 5 you also need `python3` with the `venv` module and the DVB-I schema files (see that section).

## 1. Run the provider

```bash
cd ~
git clone https://github.com/5G-MAG/rt-dvb-i-application-provider.git
cd rt-dvb-i-application-provider
npm install
npm start
```

```text
{"time":"2026-10-21T18:59:19.299Z","level":"info","msg":"No config.json, started from config.example.json","path":"..."}
{"time":"2026-10-21T18:59:19.302Z","level":"info","msg":"DVB-I Application Provider and Admin Portal listening (http)","port":4000}
DVB-I Application Provider and Admin Portal  →  http://localhost:4000
Service list    →  http://localhost:4000/service-list.xml
```

The first start copies `config.example.json` to `config.json`. That file is your service list from now on. (To keep `config.json` and the `config-history` folder outside the clone, set `DVBI_DATA_DIR` to a folder of your own before `npm start`.) In a second terminal, read the list, check how it is served, and ask the server about itself:

```bash
curl -s http://localhost:4000/service-list.xml | head -12
curl -sI http://localhost:4000/service-list.xml | grep -i content-type
curl -s http://localhost:4000/api/health
```

```xml
<?xml version="1.0" encoding="UTF-8"?>
<ServiceList
  xmlns="urn:dvb:metadata:servicediscovery:2024"
  xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xmlns:hls="vnd:apple:mpegurl"
  xmlns:tva="urn:tva:metadata:2024"
  xmlns:dvbisd-t="urn:dvb:metadata:servicediscovery-types:2023"
  id="tag:5g-mag.org,2026:servicelist:local-demo"
  version="2" xml:lang="en">

  <Name>5G-MAG</Name>
  <ProviderName>DVB-I Demo</ProviderName>
```

```text
Content-Type: application/vnd.dvb.dvbisl+xml; charset=utf-8
```

```text
{"status":"ok","version":2,"services":3}
```

The stock list has three channels (Tears of Steel, an Akamai UHD test stream and an Akamai live test stream). It is named `5G-MAG` and has the Service List ID `tag:5g-mag.org,2026:servicelist:local-demo`, the same name and identifier as the stock entry of the [DVB-I Service List Registry](./service-list-registry). The list is served with the media type `application/vnd.dvb.dvbisl+xml` that TS 103 770 V1.2.1 clause 5.1.2 requires for a Service List. The `version` attribute is the number of the list; the specification says it shall be incremented for every published change (clause 5.5.1, table 14, `@version`), and the provider does it each time you press **Save & Publish**.

## 2. The admin portal

Open `http://localhost:4000/` in a browser.

![The admin portal: the toolbar, the service list settings and the first channel](/img/dvb-i/tut-dvbi-provider-admin.png)

| Where | What it is |
|---|---|
| Toolbar | **Import XML**, **Download XML**, **Validate**, **Compliance**, **History** and **Save & Publish** |
| Receiver URL | The address clients fetch the list from, with a **Copy** button |
| Service List Settings | The name of the list, the provider, the content guide source, the language, the target country and the **Service List ID** |
| Services | One row for each channel: **Clone**, **Edit**, **Delete**, the up and down arrows, and the **On** switch. The selector next to **Load Template** offers ready-made starting points |
| Generated XML | The XML the list produces, with **Refresh** and **Copy** |

The portal saves nothing until you press **Save & Publish**: it rewrites `config.json` and raises the version of the list.

## 3. Add a channel and publish

The routine for every change: edit in the portal, **Save Service** in the editor, **Save & Publish**, then read the published XML.

1. In the services toolbar, choose **Reference service (all fields, DASH)** in the selector and press **Load Template**. The editor opens with every field filled in; the template does not set a period of availability, so the channel is open-ended.
2. Change these fields:

   | Field | Value |
   |---|---|
   | Service Name | `Tutorial Channel` |
   | LCN | `4` |
   | Unique ID (UID) | `tag:example.com,2026:service:tutorial-channel` |
   | Multi-language service names, `en` line | `Tutorial Channel` (the names there replace the Service Name in the published list) |
   | Stream URL of the DASH instance | `https://dash.akamaized.net/dash264/TestCasesUHD/2b/11/MultiRate.mpd`, the DASH stream the stock list already uses |
   | Target Region (under the instances) | empty |
   | Subscription Package | empty |

   ![The service editor, filled in from the template](/img/dvb-i/tut-dvbi-provider-edit-service.png)

3. Press **Save Service**, then **Save & Publish**.

**Check** the published list: the channel is in it, and the version has gone up.

```bash
curl -s http://localhost:4000/service-list.xml | grep -n -E 'version="[0-9]+" xml:lang|channelNumber="4"|>Tutorial Channel<'
```

```text
9:  version="3" xml:lang="en">
24:      <LCN channelNumber="4" serviceRef="tag:example.com,2026:service:tutorial-channel"/>
174:    <ServiceName xml:lang="en">Tutorial Channel</ServiceName>
```

(The stock list was version 2, so the first publish makes it 3.) The template sets no period of availability, so the list has none either:

```bash
curl -s http://localhost:4000/service-list.xml | grep -c -i -E 'availability|validFrom'
```

```text
0
```

The list is served with `Last-Modified`, and a client that sends `If-Modified-Since` gets `304 Not Modified` until you publish again (clause 4.3.2.2):

```bash
LM=$(curl -sI http://localhost:4000/service-list.xml | grep -i last-modified | cut -d' ' -f2- | tr -d '\r')
curl -s -o /dev/null -w '%{http_code}\n' -H "If-Modified-Since: $LM" http://localhost:4000/service-list.xml
```

```text
304
```

## 4. Recipes

Each recipe is the routine of section 3 with a different edit.

### 4.1 Programmes for a channel

The template already carries two programmes for its channel, **Morning Report** (60 minutes) and **The Long Road** (45 minutes). In the editor they are under the programmes heading; each has a title, a duration in minutes, a synopsis, and optional image, series, episode, age, genre and catch-up fields. **+ Add Programme** adds a row.

The provider turns the programmes into a schedule that repeats them in order, from two hours before the current hour to eight hours after now. Ask for it with the unique ID of the channel (the guide takes it as `sid`):

```bash
curl -s 'http://localhost:4000/epg/nownext?sid=tag:example.com,2026:service:tutorial-channel'
```

```xml
<?xml version="1.0" encoding="UTF-8"?>
<TVAMain xmlns="urn:tva:metadata:2024" xmlns:mpeg7="urn:tva:mpeg7:2008" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns:tva="urn:tva:metadata:2024" xml:lang="en">
  <ProgramDescription>
    <ProgramInformationTable>
    <ProgramInformation programId="crid://dvbi.example.com/2024/prog/0">
      <BasicDescription>
        <Title type="main">Morning Report</Title>
        <Synopsis length="short">The day&apos;s news, business and weather.</Synopsis>
```

(The answer goes on with the second programme and the two schedule events. Which programme is first, and the times, depend on your clock.) `/epg/schedule?sid=...` returns the whole window in the same format. A channel with no programmes gets a valid, empty `TVAMain` document with status 200.

### 4.2 Switch a channel off

Press **On** on a channel; it changes to **Off**. Press **Save & Publish**. The channel and its channel number leave the published list, and the version goes up. Press **Off**, then **Save & Publish**, to bring it back.

```bash
curl -s http://localhost:4000/service-list.xml | grep -c '<Service '
```

```text
3
```

(That is the count with one of four channels off.)

### 4.3 Go back to an earlier list

Press **History**: it lists the lists you published before, newest first, each with its version and the number of services. Press **Restore** on one, and confirm. The restored list is published at once, and it gets a new version, above every version the provider has published so far, not the old number (clause 5.5.1). The services in it follow the same rule: the version of a service (clause 5.5.2, table 15) is raised above every version published for that service, so a number is never used for two different descriptions of a service.

```bash
curl -s http://localhost:4000/api/health
```

```text
{"status":"ok","version":5,"services":4}
```

After **Restore** on the oldest entry (the stock list, 3 services) the same request answers:

```text
{"status":"ok","version":6,"services":3}
```

The first entry of **History** is now the list you left; press **Restore** on it to come back, and the version becomes 7 with 4 services. Check that the channel is back:

```bash
curl -s http://localhost:4000/service-list.xml | grep -c 'channelNumber="4"'
```

```text
1
```

## 5. Check what you published

**In the portal.** Press **Validate** for the checks on the list: the names, the Service List ID (it must be a URI, clause 5.2.2), unique channel numbers and identifiers, and a stream and a valid address for every channel. The stock list passes all 11 checks on a fresh install, and so does the list of this page.

![The Service List Validation dialog, 11 of 11 checks passed](/img/dvb-i/tut-dvbi-provider-validate.png)

Press **Compliance** for a longer set of checks against TS 103 770 and DVB document A184r2 on the current list, or on an external one by address or file. On the list of this page it reported 38 of 38 checks passed and "Fully compliant". A list that carries the 5G-MAG extension instead gets a warning, "Local extension (outside the DVB schema)"; see [Tutorial: DVB-I over 5G Broadcast](./dvb-i-over-5g-broadcast#2-publish-a-service-on-5g-broadcast-and-unicast).

**Against the schema.** The repository does not carry schema files. You supply them from a folder outside the clone.

1. Put the schema files in one folder, for example `~/dvb-i-schemas`. The specification's electronic attachment archive `ts_103770v010201p0.zip` has the base schema `dvbi_v6.0.xsd` and its imports (TS 103 770 V1.2.1, annex B); the steps to download it are in [Tutorial: DVB-I Service List Registry](./service-list-registry#5-check-a-response-against-the-schema). The stock list carries HLS instances, which the base schema does not know, so the check needs the schema that adds the HLS and HbbTV extensions: `dvbi_v6.0+hls+hbbtv.xsd`, with `hls-url-6.0.xsd` and `hbbtv-ext-6.0.xsd`. A third party publishes them (see the note below), together with `tva_metadata_3-1_2024.xsd`, the file name that `dvbi_v6.0+hls+hbbtv.xsd` imports. With the files of the archive and `xml.xsd` already in the folder, add the four:

   ```bash
   cd ~/dvb-i-schemas
   for f in 'dvbi_v6.0+hls+hbbtv.xsd' hls-url-6.0.xsd hbbtv-ext-6.0.xsd tva_metadata_3-1_2024.xsd; do
     curl -s -o "$f" "https://raw.githubusercontent.com/paulhiggs/dvb-i-tools/main/schemas/$f"
   done
   ```

2. Run the repository's own check:

   ```bash
   DVBI_SCHEMAS=~/dvb-i-schemas npm run test:xsd
   ```

   ```text
   Schemas: ~/dvb-i-schemas
     service list: dvbi_v6.0+hls+hbbtv.xsd
     TV-Anytime:   tva_metadata_3-1_2024.xsd

   DVB-I / TV-Anytime XSD conformance test

   Service list (comprehensive sample):
     ✓ service-list.xml: VALID

   Service list (live config.json):
     ✓ config.json: VALID

   Service list (local 5G extension):
     ~ hybrid unicast + 5G: NOT CONFORMANT GROUND — carries the LOCAL 5G delivery extension (urn:5g-mag:metadata:dvbi-5g:2026), which no published schema defines. Valid against the published schema composed with schemas/dvbi-5g-ext-1.0.xsd; that is not conformance to TS 103 770. See COMPLIANCE.md.

   Service list (templates/):
     ✓ dvbi-local-live-demo.json: VALID
     ✓ service-template.json: VALID

   EPG (live config.json endpoints):
     ✓ epg-schedule.xml: VALID
     ✓ epg-nownext.xml: VALID

   ==== ALL VALID (1 not checked, see above) ====
   ```

   (The path on the first line is the folder you gave. The `NOT CONFORMANT GROUND` line is the test's own sample of a service on unicast and 5G; it is about the 5G broadcast extension, which no DVB schema defines, and the [DVB-I over 5G Broadcast](./dvb-i-over-5g-broadcast) tutorial covers it. With only the files of the ETSI archive in the folder, the lists that carry HLS are reported as `NOT CHECKED`, because `dvbi_v6.0.xsd` has no HLS extension.)

3. Check the list you published yourself with the `check.py` of [Tutorial: DVB-I Service List Registry](./service-list-registry#5-check-a-response-against-the-schema):

   ```bash
   curl -s http://localhost:4000/service-list.xml > list.xml
   ~/dvbi-check/bin/python check.py "$HOME/dvb-i-schemas/dvbi_v6.0+hls+hbbtv.xsd" list.xml
   ```

   ```text
   VALID: list.xml
   ```

   Against the base `dvbi_v6.0.xsd`, the same stock list is reported invalid, because the schema does not know `m3u8RefType` (the HLS instances). A list with DASH instances only is not affected by that.

:::note[Where the schema files for this page came from]
The base files (`dvbi_v6.0.xsd`, `dvbi_types_v1.0.xsd`, `tva_mpeg7.xsd`) are from the ETSI archive and `xml.xsd` is from the W3C. The files that add HLS and HbbTV, and `tva_metadata_3-1_2024.xsd`, are copies from the `schemas` folder of a third-party repository, [paulhiggs/dvb-i-tools](https://github.com/paulhiggs/dvb-i-tools), because they are not in the ETSI archive. `tva_metadata_3-1_2024.xsd` is not identical to the archive's `tva_metadata_3-1.xsd`: a diff, after removing line-ending differences, showed four differing lines (the two import paths, and the `minOccurs` and `maxOccurs` of the `ScheduleEvent` and `Purpose` elements). The repository's check accepts either file name.
:::

## 6. Close the admin

Without a token, anyone who can reach the port can change the list and upload logos. Start the provider with `ADMIN_TOKEN` set before anyone else can reach it (`DEPLOYMENT.md`):

```bash
ADMIN_TOKEN="$(openssl rand -hex 24)" npm start
```

With a token set, the admin routes need `Authorization: Bearer <token>`, and the portal asks for the token the first time it is refused. The list and the guide stay public. Check with a second instance on another port:

```bash
ADMIN_TOKEN=secret123 PORT=4100 npm start
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:4100/api/config
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer secret123' http://localhost:4100/api/config
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:4100/service-list.xml
```

```text
401
200
200
```

:::note[TLS beyond a private network]
TS 103 770 V1.2.1, clause 7.3, says a DVB-I client uses HTTP over TLS to reach a Service List Server and a Content Guide Server, and allows plain HTTP only on the same private subnet as the client. The provider can serve HTTPS itself: set `HTTPS_KEY_PATH` and `HTTPS_CERT_PATH` to the paths of a PEM key and certificate, or terminate TLS in a reverse proxy (`DEPLOYMENT.md`).
:::

## 7. Stop and clean up

Press Ctrl+C in the terminal of each instance. To remove the provider, delete `~/rt-dvb-i-application-provider`, `~/dvb-i-schemas` and `~/dvbi-check`.

<summary>What was run for this page</summary>

Every command above was run on a clean clone of `main` (commit `e3cfb1e`, which includes the fixes of TS 103 770 V1.2.1 behaviour) on Ubuntu Linux with Node.js 24.21.0 and npm 11.19.0, Python 3.14.4 and lxml 6.1.3 (libxml2 2.14.6). The portal steps were driven in a headless Chromium (Playwright 1.61.1, Chromium 149.0.7827.55), which is also how the three pictures were taken. The page was last re-run on 2026-10-21.

Section by section: 1 run (the list, its `Content-Type` and `/api/health` read back; `DVBI_DATA_DIR` was run once with a folder of its own, and `config.json` and `config-history` were created there); 2 run (the portal opened and read); 3 run (the template loaded and changed as in the table, saved, published; the version, the channel number and the `304` read back; no availability period in the published XML); 4.1 run (`/epg/nownext` and `/epg/schedule` read and checked against the schema); 4.2 run (off, publish, count, on, publish); 4.3 run (History, **Restore** of the oldest entry, then of the newest; the versions 6 and 7 read from `/api/health`; the version of each service was read from the XML but the rule for services is taken from the code and its changelog, and was not tested case by case); 5 run (**Validate** 11 of 11 on the stock list and on the list of this page, **Compliance** 38 of 38 and "Fully compliant", `npm run test:xsd` and `check.py` valid); 6 run for the token on a second instance, and not run for HTTPS (`HTTPS_KEY_PATH` and `HTTPS_CERT_PATH` are from `DEPLOYMENT.md`).

Whether the stream URLs play was not part of this page's checks. A valid list and a published channel are what the provider is responsible for; the picture is checked in [Tutorial: DVB-I Application](./dvb-i-application).
