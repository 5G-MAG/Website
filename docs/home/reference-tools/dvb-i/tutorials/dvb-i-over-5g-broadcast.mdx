<h1>Tutorial: DVB-I over 5G Broadcast</h1>

A DVB-I service can be offered on 5G Broadcast and on unicast at the same time. ETSI TR 103 972 V1.1.1 clause 6.4.3.1 models it as two service instances of one service, and clause 6.4.3.2 says the 5G Broadcast instance may be given the higher priority with the `@priority` attribute of the service instance. In this tutorial you publish such a service with the DVB-I Application Provider and open it in the DVB-I Application, the browser client.

This tutorial is about the signalling in the service list. Receiving the broadcast needs an MBMS Client on the device (TS 103 770 V1.2.1 clause 9.3.3); no repository of this project provides one yet, so the client plays the unicast instance (section 3).

:::tip[Read the READMEs first]
Read the README of [rt-dvb-i-application-provider](https://github.com/5G-MAG/rt-dvb-i-application-provider#readme) before you start; its section "The local 5G broadcast extension" is the part this tutorial uses. Read the README of [rt-dvb-i-application](https://github.com/5G-MAG/rt-dvb-i-application#readme) when you reach section 3.
:::

## 1. Run the provider

```bash
cd ~
git clone https://github.com/5G-MAG/rt-dvb-i-application-provider.git
cd rt-dvb-i-application-provider
npm install
npm start
```

```text
DVB-I Application Provider and Admin Portal  →  http://localhost:4000
Service list    →  http://localhost:4000/service-list.xml
```

In a second terminal:

```bash
curl -s http://localhost:4000/api/health
```

```text
{"status":"ok","version":2,"services":3}
```

The stock list has three channels. [Tutorial: DVB-I Application Provider](./application-provider) explains the admin portal.

## 2. Publish a service on 5G Broadcast and unicast

The routine is that of the provider tutorial, sections 1 and 3: edit in the portal, **Save Service**, **Save & Publish**, then read the published XML. Open `http://localhost:4000/`.

1. In the services toolbar, choose **Reference service (all fields, DASH)** and press **Load Template**.
2. Change these fields:

   | Field | Value |
   |---|---|
   | Service Name | `Hybrid Tutorial Channel` |
   | LCN | `4` |
   | Unique ID (UID) | `tag:example.com,2026:service:tutorial-hybrid` |
   | Multi-language service names, `en` line | `Hybrid Tutorial Channel` |
   | Target Region (under the instances) | empty |
   | Subscription Package | empty |

3. The template has one instance, of type **DASH**. Set its **Priority** to `2`, its **Label** to `Hybrid Tutorial Channel (unicast DASH)` and its **Stream URL** to `https://dash.akamaized.net/dash264/TestCasesUHD/2b/11/MultiRate.mpd`, a public DASH test stream.
4. Press **+ Add Instance**. In the new instance, choose the type **5G / MBMS (extension)** and set:

   | Field | Value |
   |---|---|
   | Priority | `1` |
   | Label | `Hybrid Tutorial Channel (5G Broadcast)` |
   | MBMS service locator | `mbms://broadcast.example.com/tutorial-hybrid` |
   | MBMS service class | empty (the provider then writes `urn:dvb:metadata:serviceClass:DVB-I_Service_Instance:1`) |
   | Unicast fallback URL | `https://dash.akamaized.net/dash264/TestCasesUHD/2b/11/MultiRate.mpd` |

   ![The two instances of the service: DASH with priority 2, and 5G / MBMS with priority 1](/img/dvb-i/tut-dvbi-5g-instances.png)

5. Press **Save Service**, then **Save & Publish**.

**Check:** the service has two instances, and the 5G one has priority 1.

```bash
curl -s http://localhost:4000/service-list.xml | sed -n '/<!-- Hybrid Tutorial Channel -->/,/<ServiceName xml:lang="en"/p' | grep -E 'ServiceInstance|DisplayName|Delivery|dvbi5g:|URI|Local ext'
```

```xml
    <ServiceInstance priority="2">
      <DisplayName>Hybrid Tutorial Channel (unicast DASH)</DisplayName>
      <DASHDeliveryParameters>
          <dvbisd-t:URI>https://dash.akamaized.net/dash264/TestCasesUHD/2b/11/MultiRate.mpd</dvbisd-t:URI>
      </DASHDeliveryParameters>
    </ServiceInstance>
    <ServiceInstance priority="1">
      <DisplayName>Hybrid Tutorial Channel (5G Broadcast)</DisplayName>
      <!-- Local extension, not DVB-specified: see schemas/dvbi-5g-ext-1.0.xsd and COMPLIANCE.md -->
      <OtherDeliveryParameters extensionName="urn:5g-mag:dvbi-5g:mbms" xsi:type="dvbi5g:MBMSDeliveryParametersType">
        <dvbi5g:ServiceLocator>mbms://broadcast.example.com/tutorial-hybrid</dvbi5g:ServiceLocator>
        <dvbi5g:ServiceClass>urn:dvb:metadata:serviceClass:DVB-I_Service_Instance:1</dvbi5g:ServiceClass>
          <dvbi5g:UnicastFallback>https://dash.akamaized.net/dash264/TestCasesUHD/2b/11/MultiRate.mpd</dvbi5g:UnicastFallback>
      </OtherDeliveryParameters>
    </ServiceInstance>
```

:::tip[A local extension, and what the portal says about it]
TS 103 770 V1.2.1 defines no delivery parameters for MBMS in its list of delivery parameter types (clauses 5.5.18.1 to 5.5.18.8), so the provider writes the 5G instance through the extension point `OtherDeliveryParameters`, with a type in the 5G-MAG namespace `urn:5g-mag:metadata:dvbi-5g:2026`. The namespace is declared in the list only when a service uses it. ETSI TR 103 972 V1.1.1 clause 6.2.4 records the missing element as a gap, and clause 6.4.3.3 prefers a separate instance type to signalling 5G Broadcast as DASH delivery. A client that does not know the namespace finds no delivery parameters it understands on that instance and uses another instance of the service.

In the portal, **Validate** passes all 11 checks for this list: the check `All stream URLs use http(s)` accepts an `mbms://` locator on an instance of type **5G / MBMS (extension)**, which is where the extension carries it, and still refuses it on any other instance. **Compliance** reports 38 of 39 checks and one warning, in a section named "Local extension (outside the DVB schema)": the list carries the 5G-MAG extension, which no DVB schema defines, so the checks above cover only what DVB specifies. It does not report such a list as "Fully compliant".
:::

## 3. See it in a DVB-I client

```bash
cd ~
git clone https://github.com/5G-MAG/rt-dvb-i-application.git
cd rt-dvb-i-application
npm install
npm start
```

Open `http://localhost:5000/?url=http://localhost:4000/service-list.xml`. Channel 4 shows a dashed badge, **5G ext**; hover over it for the tooltip, which names the extension and says it is local and not defined by any DVB specification. Select the channel, or press **4**.

![The DVB-I Application with the Hybrid Tutorial Channel selected and its 5G ext badge](/img/dvb-i/tut-dvbi-5g-client.png)

*The picture area is black in this capture because it was taken in a headless browser without video codecs. In your browser the stream plays.*

**Check:** which instance played. Open the developer tools of the browser on the **Network** tab. The client requested `MultiRate.mpd` and its segments from `dash.akamaized.net`, all with status 200, and made no request to an `mbms://` address: a browser cannot join an MBMS bearer, so it uses the unicast instance.

<details>
<summary>A service with the 5G instance and a unicast fallback only</summary>

The `Unicast fallback URL` of the extension is also played. The client turns it into a separate unicast instance with a lower priority than the 5G instance (the priority of the 5G instance plus one), following the model of TR 103 972 clauses 6.4.3.1 and 6.4.3.2: unicast and 5G as two service instances, the 5G one with the higher priority. The new instance takes the content protection and the content attributes of the 5G instance, and its media type from the `type` attribute of the extension element, else from the URL (`.m3u8` is HLS, `.mpd` is DASH), else DASH. It is not added when the service already lists the URL, which is the case in this section, because the DASH instance has the same URL. `UnicastFallback` is a local extension, not part of TS 103 770 or TR 103 972.

To see it, edit the channel in the portal, remove the DASH instance with the **✕** at the end of its row, press **Save Service**, then **Save & Publish**, and reload the client. The channel keeps its **5G ext** badge and, when you select it, the client requests `MultiRate.mpd` from the fallback URL and makes no request to an `mbms://` address. The **AD** and **HoH** badges are gone, because they belonged to the DASH instance and the 5G instance declares none.

## 4. What a receiver does with the instance

With an MBMS Client on the device, the specifications give the receiver these steps for an instance that carries an `mbms://` locator:

| Step | What happens | Specification |
|---|---|---|
| The service class is read | The MBMS Client exposes the service class of each MBMS User Service to the DVB-I client, which acts as an MBMS-Aware Application. A service instance is conveyed in a User Service of class `urn:dvb:metadata:serviceClass:DVB-I_Service_Instance:1` | ETSI TS 103 770 V1.2.1 clauses 9.3.1 (table 106) and 9.3.2; 3GPP TS 26.346 V19.3.0 clause 11.2.1.2 |
| The locator is read | An `mbms://` URL has a prefix that is the `serviceId` of the MBMS User Service, and an optional `&label=` suffix for one resource | 3GPP TS 26.347 V18.1.0 clause 8.2.2 |
| The instance is selected | The DVB-I client invokes the MBMS Client to start reception of the User Service, then passes the application entry point document (for example the DASH MPD) that the User Service Description references to the media player | ETSI TS 103 770 V1.2.1 clause 9.3.3 |
| Reception starts | The MBMS-Aware Application selects the streaming service, the MBMS Client receives the MPD and segments and stores them in its Media Server, and the player reads them from there | ETSI TR 103 972 V1.1.1 clause 6.2.3.4, steps 33 to 48; 3GPP TS 26.347 V18.1.0 clause 6.3 |
| The instance is chosen among others | The signalled `@priority` is respected; lower values mean higher priority; an instance with video or audio that the client could not present is discarded | ETSI TS 103 770 V1.2.1 clauses 5.2.13 and 5.5.4 |

The second instance with priority 2, and the unicast fallback in the extension, are what a client without an MBMS Client plays.

:::note[Two ways to write the locator]
TS 103 770 V1.2.1 clause 9.3.3 speaks of "a DVB-I service instance with an mbms:// locator" but names no element for it, and ETSI TR 103 972 V1.1.1 clause 6.2.4 records that as a gap. The service list does define `IdentifierBasedDeliveryParameters` (clause 5.5.18.8), "An identifier in the form of a locator (URL) or name (URN)". The Android client of [rt-dvb-i-android-application](https://github.com/5G-MAG/rt-dvb-i-android-application) reads an `mbms://` locator from that element, checks it against TS 26.347 clause 8.2.2 and shows a 5G Broadcast badge; the provider and the browser client of this tutorial use the 5G-MAG extension of section 2 instead. A list written by the provider therefore shows the 5G instance as a 5G extension in the browser client, and the Android client treats it as a delivery it does not know and plays the DASH instance (`Instances.kt`, `ServiceListParser.kt` in rt-dvb-i-android-application).
:::

## 5. Check what you published

**Against the schema.** The repository does not carry schema files; you supply them from a folder outside the clone, as in [Tutorial: DVB-I Application Provider](./application-provider#5-check-what-you-published). With your schema folder in `~/dvb-i-schemas`:

```bash
cd ~/rt-dvb-i-application-provider
DVBI_SCHEMAS=~/dvb-i-schemas npm run test:xsd
```

```text
Service list (live config.json):
  ~ config.json: NOT CONFORMANT GROUND — carries the LOCAL 5G delivery extension (urn:5g-mag:metadata:dvbi-5g:2026), which no published schema defines. Valid against the published schema composed with schemas/dvbi-5g-ext-1.0.xsd; that is not conformance to TS 103 770. See COMPLIANCE.md.
```

The line says that the list carries the local 5G delivery extension, which no published schema defines, that it is valid against the published schema composed with `schemas/dvbi-5g-ext-1.0.xsd`, and that this is not conformance to TS 103 770, which defines no such type. The stock channels of this list carry HLS as well as the 5G instance; with the schema folder of the provider tutorial (which has the HLS extension) the list is checked as above, and with only the files of the ETSI archive it is reported as `NOT CHECKED` because of the HLS instances. The run ends with `==== ALL VALID (2 not checked, see above) ====`.

**In the portal.** **Compliance** runs its structural checks on the list; for this list it reported 38 of 39 checks passed and one warning, "Local extension (outside the DVB schema)", as in section 2.

## 6. Stop and clean up

Press Ctrl+C in the terminal of the provider and of the client. To remove them, delete `~/rt-dvb-i-application-provider` and `~/rt-dvb-i-application`.
