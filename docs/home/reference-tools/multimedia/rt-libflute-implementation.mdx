## What this page is

[rt-libflute](https://github.com/5G-MAG/rt-libflute) is 5G-MAG's open-source C++ library for FLUTE &mdash; the protocol used to push files (media segments, manifests, service metadata) one-way over a multicast or broadcast network, with no return channel from the receiver. This page states, feature by feature, which capabilities the library implements against 3GPP TS 26.346 and the FLUTE RFCs. Every area below follows the same pattern: a table you can scan in a few seconds, then a step-by-step account of exactly how each supported feature works, citing the specific clause it was checked against.

The specifications named here are explained and listed in full on the companion page, [rt-libflute Specifications](./rt-libflute-standards) &mdash; including why FLUTE version 1, not the newer version 2, is the profile that applies to 5G-MAG's use of this library. This page doesn't repeat that list; every RFC and TS number below is one already collected there.

:::note[Key terms]
- **FLUTE**: File Delivery over Unidirectional Transport &mdash; the protocol this library implements. **ALC** / **LCT**: the two lower-level building blocks FLUTE is built on (congestion control and packet framing, respectively).
- **FDT**: File Delivery Table &mdash; a special FLUTE object (always sent with TOI 0) listing every file currently available in the session and how to decode it. Resent repeatedly ("carousel") so a receiver joining mid-session can still discover everything.
- **TOI** / **TSI**: Transport Object Identifier (which file a packet belongs to) and Transport Session Identifier (which session). Every FLUTE packet carries both.
- **FEC**: Forward Error Correction &mdash; redundant data that lets a receiver reconstruct a file even if some packets are lost, without a return channel to ask for a resend.
:::

:::note[Audit baseline]
This page describes the `development` branch as of 2026-08-11. It is a source-level reading of the code against the specification text, not a maintainer sign-off.
:::

## Protocol core: FLUTE / ALC / LCT

| Feature | Standard | Implemented? |
| --- | --- | --- |
| FLUTE version 1 on the wire | RFC 3926; TS 26.346 §7.2.0 | **Yes** |
| LCT header fields (CCI, TSI, TOI, flags) | TS 26.346 §7.2.7 | **Yes** |
| LCT extension headers (EXT_FDT, EXT_FTI, EXT_CENC) | TS 26.346 §7.2.8 | **Yes** |
| Close Session / Close Object flags | TS 26.346 §7.2.7 | No &mdash; parsed on receive, not settable on transmit |
| TSI wider than 16 bits | RFC 3451/5651 §4.2 (S/H flags) | No &mdash; not needed for MBMS, see step 2 below |
| FDT Instance ID wraparound | RFC 3926 §3.4.1 | No &mdash; ID increments without bound instead of wrapping |

**How this works**

1. **FLUTE version.** Every FDT-carrying packet's EXT_FDT extension is stamped with version 1 in its high nibble on transmit. The decoder additionally tolerates a version 2 nibble on receive. This matches RFC 3926's own text: "This document specifies FLUTE version 1... in any ALC packet that carries FDT Instance... MUST set this field to '1'."
2. **LCT header.** TS 26.346 §7.2.7 fixes several fields for MBMS specifically, and the implementation matches each one: the CCI field is 32 bits and always zero; the TSI field is a 16-bit half-word (S=0, H=1); the TOI field is a 16-bit half-word on transmit (the decoder accepts a wider TOI, since nothing in the clause forbids a receiver being more permissive); TOI 0 is reserved exclusively for FDT Instances; the Sender-Current-Time and Expected-Residual-Time flags are always zero; HDR_LEN is expressed in 32-bit words as required.
3. **LCT extensions.** Per §7.2.8's exact rule, EXT_FDT and EXT_FTI are generated on every FDT Instance (TOI 0) packet and omitted from every file (TOI&gt;0) packet. EXT_CENC is decoded on receive but never generated on transmit, since §7.2.8 separately states FDT Instances shall not be content encoded. EXT_NOP, EXT_AUTH and EXT_TIME are accepted and ignored on receive, which is RFC 3926's own default action for unrecognised extensions.

## Forward Error Correction

| Feature | Standard | Implemented? |
| --- | --- | --- |
| Compact No-Code FEC | RFC 3695; TS 26.346 §7.2.2, §7.2.3 | **Yes** |
| Raptor FEC | RFC 5053; TS 26.346 §7.2.2 (decoder mandatory), §7.2.12, Annex B | **No** |
| RaptorQ FEC | RFC 6330 | No &mdash; not part of TS 26.346's FEC scheme set |

**How this works**

1. **Compact No-Code.** The FEC Payload ID is a 16-bit Source Block Number plus a 16-bit Encoding Symbol ID, exactly as RFC 3695/TS 26.346 §7.2.7 specify. Source-block partitioning follows RFC 3926's "Algorithm for Computing Source Block Structure," referenced by §7.2.3. This scheme works correctly, but it is not the scheme TS 26.346 actually depends on for reliability &mdash; it carries no redundancy at all, so any lost packet loses that piece of the file until the next FDT carousel cycle.
2. **Raptor is the gap that matters most on this page.** §7.2.2 states plainly: "A UE that supports MBMS User Services shall support a decoder for the Raptor FEC scheme." That decoder does not exist in `development` today. Everything else on this page is either done or a smaller gap; this is the one place where the implementation falls short of a hard MUST-level requirement that's central to what MBMS/MBS download is for.
3. **RaptorQ** is a newer, unrelated FEC scheme (RFC 6330). It doesn't appear anywhere in TS 26.346's FEC scheme definitions (§7.2.2, §7.2.12) &mdash; not required, not forbidden, simply outside this standard's scope.

## FDT Instances

| Feature | Standard | Implemented? |
| --- | --- | --- |
| Mandatory FDT attributes (Content-Location, TOI, Expires) | TS 26.346 §7.2.9 | **Yes** |
| Optional FDT attributes (Content-Length, Content-Type, Content-MD5, FEC-OTI-*) | TS 26.346 §7.2.9 | **Yes** |
| 3GPP FDT extensions (Cache-Control, File-ETag) | TS 26.346 §7.2.10, §7.2.13 | **Yes** |
| FDT expiry hard enforcement | TS 26.346 §7.2.9 | Partial &mdash; parsed, not enforced at packet-processing time |
| Complete attribute | RFC 3926 §3.4.2; TS 26.346 §7.2.9 | No |
| Group, Session-Identity, FullFDT, Decryption-KEY-URI, FEC-Redundancy-Level | TS 26.346 §7.2.6, §7.2.11, §7.2.14&ndash;7.2.16 | No |

**How this works**

1. **Mandatory attributes.** Every FDT Instance and File entry carries Content-Location, TOI and Expires &mdash; the three data elements §7.2.9 marks as mandatory &mdash; read on receive and written on transmit.
2. **Optional attributes.** Content-Length, Content-Type, Content-Encoding, Content-MD5, and the FEC-OTI-* attributes are all read and written, matching the optional set §7.2.9 lists. Content-MD5 in particular is actively checked: on reception, a mismatch against the decoded content triggers re-reception rather than silently accepting a corrupt file.
3. **3GPP FDT extensions.** The `mbms2007:Cache-Control` element (no-cache, Expires) and `mbms2012:File-ETag` attribute, both defined in §7.2.10's schema extensions, are read and written.
4. **FDT expiry is the one genuinely partial case on this page.** §7.2.9 requires: "the UE shall not use a received FDT Instance to interpret packets received beyond the expiration time." The Expires value is parsed and made available to callers (cache-eviction logic reads it), but nothing in the packet-receive path itself checks an FDT Instance's expiry before using it to interpret an incoming packet. The common case is covered by cache eviction; the hard, spec-mandated cutoff at packet-processing time is not yet there.

## Content encoding

| Feature | Standard | Implemented? |
| --- | --- | --- |
| GZIP encode (transmit) / decode (receive) | RFC 1952; TS 26.346 §7.2.5 | **Yes** |
| FDT Instances never content encoded | TS 26.346 §7.2.8 | **Yes** |

**How this works**

1. Files are GZIP-encoded on transmit and decoded on receive, satisfying §7.2.5's UE mandate; decoded length is checked against the FDT's declared Content-Length as a correctness check. Deflate is also handled.
2. FDT Instances themselves are never content-encoded on transmit, matching §7.2.8's separate rule for FDT Instances specifically (distinct from the file content-encoding rule above).

## Transport, session and platform

| Feature | Standard | Implemented? |
| --- | --- | --- |
| UDP multicast, IPv4 and IPv6 | &mdash; | **Yes** |
| UDP tunnel mode (GTP-U user plane) | TS 23.247 (N3mb) | **Yes** |
| IPsec ESP protection | &mdash; | **Yes** |
| Source-Specific Multicast (SSM) | RFC 4607 | Partial &mdash; IPv4 only |
| Multicast join on a specific interface | &mdash; | Partial &mdash; IPv4 only |
| Receive buffer sized to the max UDP datagram | &mdash; | No &mdash; fixed well below that today |

**How this works**

1. Transmit and receive both work over plain UDP multicast on IPv4 and IPv6.
2. Tunnel mode wraps each packet in an encapsulated IPv4+UDP inner header for delivery through a GTP-U user plane &mdash; the N3mb transport context TS 23.247 defines, used by rt-mbs-transport-function.
3. IPsec ESP protects the transport in both directions via Linux XFRM/netlink.
4. SSM (RFC 4607) and interface-selective multicast join are both implemented for IPv4 only; the IPv6 paths for the same features are not yet at parity.

## What the library deliberately doesn't do

rt-libflute implements the FLUTE/ALC/LCT protocol layer and FEC &mdash; the transport itself. The layers around it are the consuming application's job, not the library's:

- SDP session descriptions for FLUTE sessions (TS 26.346 §7.3): parsed/generated by rt-mbms-client, rt-mbs-client and the transport functions.
- Service announcement / User Service Description (§5.2) &mdash; how a receiver discovers a session exists in the first place.
- Associated delivery procedures: file repair (§9.3), reception reporting (§9.4), consumption reporting (§9.4A) &mdash; all of which need a return channel, which this protocol by design doesn't have.
- OMA Push (§7.4), RTSP session control (§7.5), Keep Updated service (§7.7), partial file handling (§7.9).
- MBSTF/MBS service APIs (TS 29.581) and MBMS client APIs (TS 26.347).

If you're looking for where those live, they're implemented in the reference tools that sit above rt-libflute: rt-mbs-transport-function, rt-mbs-client, rt-mbms-bmsc, and rt-mbms-client.
