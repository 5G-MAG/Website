## MBS Service Layer Aspects

This page summarises the MBS user-service layer: the higher-level abstraction (defined in [TS 26.502](https://www.3gpp.org/dynareport/26502.htm)) that sits on top of the low-level MBS Services, the control-plane and user-plane functions that realise it (the MBSF and the MBSTF), and the reference points that connect them (TS 26.502 V19.6.0 clause 1, 4.1, 4.2.2). It complements the [Service and System Aspects](/tech/5g-mbs/architecture/system) page, which covers the underlying 5G Core architecture, and the [RAN Aspects](/tech/5g-mbs/architecture/system#ng-ran) page, which covers the radio side.

Two points apply to every figure and interaction described below (stated once here rather than repeated per figure):

:::note[Security architecture]
The user-plane security architecture is a dedicated, optional **MBS Security Function (MBSSF)**, defined in TS 23.247 Clause 6.13 and TS 33.501, which realises the user-plane client authentication procedure (TS 33.501 Clause W.4.1.3) at reference point **MBS-10** between the MBSSF and the MBSF Client (TS 26.502 V19.6.0 clause 4.3.4A, 4.4.1; TS 33.501 V17.16.0 clause W.4.1.1, W.4.1.3). The three specifications defining the MBSSF do not fully agree on how it relates to the MBSF/MBSTF (TS 23.247 V20.0.0 clause 6.13; TS 33.501 V17.16.0 clause W.4.1.1; TS 26.502 V19.6.0 clause 4.3.4A): TS 23.247 Clause 6.13 says the security function "is implemented in the MBSF/MBSTF" (TS 23.247 V20.0.0 clause 6.13); TS 33.501 Annex W.4.1.1 says it "needs to be collocated with either MBSF or MBSTF" (TS 33.501 V17.16.0 clause W.4.1.1); TS 26.502 Clause 4.3.4A alone describes it as an optional entity that "may be co-located with the MBSF or with the MBSTF" (TS 26.502 V19.6.0 clause 4.3.4A). This page follows TS 26.502's framing, but a reader checking TS 23.247 or TS 33.501 directly will find different wording.

Checked directly against TS 33.501 (V17.16.0, Release 17, the newest issue of TS 33.501 in the specification corpus used for this check): Clause W.4.1.3 confirms the mechanism in more detail: the MBSSF "takes the role of the BM-SC" from the legacy MBMS security architecture (TS 33.246), and the UE authenticates to the MBSSF using either **GBA** (Generic Bootstrapping Architecture, as in MBMS security) or **AKMA** (Authentication and Key Management for Applications, TS 33.535): when AKMA is used, the MRK (the UE-to-MBSSF authentication key) is derived from KAF, and the MUK (which protects MSK delivery) is set to KAF (TS 33.501 V17.16.0 clause W.4.1.3; TS 33.246 V19.0.0 clause 3.1). The MBS Traffic Key (MTK), which protects the traffic itself, is defined in TS 33.501 V17.16.0 Clause W.4.1.2, and the protection of the traffic transmission is covered separately by TS 33.501 V17.16.0 Clause W.4.2 ("Protection of the traffic transmission"), which in turn applies TS 33.246 Clauses 6.6.2/6.6.3 (protection of streaming data and download data respectively).
:::

:::note
Where the MBS Application Provider (the AF/AS) is deployed outside the Trusted Data Network (DN), it reaches the control-plane functions via the Network Exposure Function (NEF) rather than directly (via reference point N33) (TS 26.502 V19.6.0 clause 4.3.1 note; TS 23.247 V20.0.0 annex A). This applies to every AF/AS interaction described below.
:::

### Reference points at a glance

The service-layer reference points used below are (TS 26.502 V19.6.0 clause 4.2.1, 4.4.1; TS 23.247 V20.0.0 clause 5.3.1):

- **Nmb10**: AF/AS provisions MBS User Services on the MBSF (via the NEF as N33+Nmb5 when outside the trusted domain) (TS 26.502 V19.6.0 clause 4.2.1, 5.3 step 2).
- **Nmb1**: MBSF provisions low-level MBS Services on the MB-SMF (TS 26.502 V19.6.0 clause 4.3.2).
- **Nmb2**: MBSF configures MBS Distribution Sessions on the MBSTF (TS 26.502 V19.6.0 clause 4.2.1, 4.3.2).
- **Nmb8**: AF/AS ingests content into the MBSTF (TS 26.502 V19.6.0 clause 4.2.1, 4.3.3.1).
- **Nmb9**: MBSTF forwards the resulting MBS data to the MB-UPF (TS 26.502 V19.6.0 clause 4.3.3.1).
- **Nmb13** (or N33+N29mb via the NEF): AF/AS provisions low-level MBS Services directly on the MB-SMF, bypassing the user-service layer (TS 23.247 V20.0.0 clause 5.3.1, annex A; TS 26.502 V19.6.0 clause 5.3 step 1).
- **N6mb**: AF/AS injects MBS data directly into the MB-UPF (used only when the user-service layer is bypassed) (TS 23.247 V20.0.0 clause 5.3.1, annex A).
- **MBS-4-MC**: multicast/broadcast user-plane delivery of MBS data (and announcements) to the MBSTF Client (TS 26.502 V19.6.0 clause 4.4.1, 4.2.4).
- **MBS-4-UC**: unicast object-repair interaction between the MBSTF Client and the MBS AS (TS 26.502 V19.6.0 clause 4.4.1).
- **MBS-5**: unicast retrieval of the MBS User Service Announcement by the MBSF Client (TS 26.502 V19.6.0 clause 4.4.1, 4.2.4).
- **MBS-7**: client API exposing received data to the MBS-Aware Application (TS 26.502 V19.6.0 clause 4.4.1).
- **MBS-10**: MBSF Client authenticates access to security-protected MBS data via the MBSSF (see the security note above) (TS 26.502 V19.6.0 clause 4.4.1).

Load-bearing acronyms used below: AF (Application Function); AS (Application Server); MB-SMF (Multicast/Broadcast Session Management Function); MB-UPF (Multicast/Broadcast User Plane Function); MBSSF (MBS Security Function); NEF (Network Exposure Function); TMGI (Temporary Mobile Group Identity); FLUTE (File Delivery over Unidirectional Transport) (TS 23.247 V20.0.0 clause 3.2; TS 26.502 V19.6.0 clause 3.3; TS 26.517 V19.3.0 clause 3.3).

## Object distribution versus packet distribution

The MBSTF supports two distribution methods, and the choice affects both what the network does and what the client sees (TS 26.502 V19.6.0 clause 4.2.3).

- In the **packet distribution method**, the MBSTF forwards ingested packet payloads with minimal processing towards the MB-UPF, and the MBSTF Client exposes the received packets directly to the MBS-Aware Application at reference point MBS-7 (TS 26.502 V19.6.0 clause 6.2, 4.4.1). This suits content that is already framed for transport, for example an RTP or MPEG-2 TS stream, where the transport framing is preserved end to end (TS 26.502 V19.6.0 clause 6.2 note 1; TS 26.517 V19.3.0 clause 7.2.3).
- In the **object distribution method**, discrete files (objects) are carried in a FLUTE session as Asynchronous Layered Coding (ALC) packets (TS 26.517 V19.3.0 clause 6.2.1, 3.3). The MBSTF Client reassembles each object from the received packets before exposing it, typically via a local HTTP server (TS 26.502 V19.6.0 clause 4.4.1; TS 26.501 V20.0.0 clause 4.9.1 item 4). Because delivery is one-way and lossy, the object method is where object repair matters: if an object arrives incomplete, the client can fetch the missing byte ranges over unicast from the MBS AS at reference point MBS-4-UC, and only falls back to returning an incomplete object when repair is unavailable or there is no time for it (TS 26.502 V19.6.0 clause 4.2.6, 5.6.1; TS 26.501 V20.0.0 clause 4.9.1 item 5).

For DASH or HLS media, the object method maps segments to objects and the presentation manifest becomes a Service Entry Point object (TS 26.502 V19.6.0 clause 6.1 table 6.1-1; TS 26.501 V20.0.0 clause 4.9.3.3). The MBSTF can operate in a _streaming_ mode, scheduling object delivery in real time from a manifest such as a DASH MPD, or in _single-shot_, _collection_ and _carousel_ modes for file delivery (TS 26.502 V19.6.0 clause 6.1 table 6.1-1). Which of these the 5G-MAG reference tools implement is listed on the [MBS Implementation Detail page](/reference-tools/5g-mbs/implementation).

## Session life-cycle and announcement

The provisioning and activation flow is time-driven (TS 26.502 V19.6.0 clause 4.5.2, 4.6.1). An MBS User Data Ingest Session may carry an activation schedule; shortly before it becomes active, the MBSF provisions the required low-level MBS Services on the MB-SMF (Nmb1) and the corresponding MBS Distribution Sessions on the MBSTF (Nmb2), after which content ingest begins at Nmb8 (TS 26.502 V19.6.0 clause 4.5.2 steps 4 and 5, 5.3). When the ingest session deactivates, the MBSF deactivates the Distribution Sessions and tears down the MBS Sessions again (for a multicast service with further active periods it only deactivates the MBS Session) (TS 26.502 V19.6.0 clause 5.5.4 steps 18 to 21). This lets a service that is not on air 24/7 (weekend sports coverage, a scheduled event) be provisioned only shortly before its active period (TS 26.502 V19.6.0 clause 4.5.2 steps 4 to 6).

Discovery is handled by the MBS User Service Announcement (TS 26.502 V19.6.0 clause 4.2.4). The MBSF builds one MBS Distribution Session Announcement per distribution session and bundles them, together with the session access information a client needs (TMGI, delivery method, media metadata), into an MBS User Service Announcement (TS 26.502 V19.6.0 clause 4.5.7, 4.5.8). Clients obtain it either by unicast pull from the MBS AF (MBS-5) or by listening to an announcement carousel delivered over MBS itself (MBS-4-MC), in band with a distribution session or out of band in a dedicated announcement session with its own TMGI (TS 26.502 V19.6.0 clause 4.2.4, 4.3.2, 4.3.3A, 5.3A). Several active services can be bundled into one announcement for efficient delivery (TS 26.517 V19.3.0 clause A.2.1).

## Service-based interfaces and protocols

The control-plane reference points (Nmb10, Nmb1, Nmb2, and the NEF-mediated variants) use 5G service-based interfaces: HTTP/2 RESTful APIs described by OpenAPI schemas, consistent with the rest of the 5G Core (TS 29.580 V20.0.0 clause 6.1.2.1; TS 29.581 V20.0.0 clause 6.1.2.1). The user-plane reference points each define concrete protocols instead: content ingest at Nmb8 is defined in TS 26.517 (TS 26.517 V19.3.0 clause 8.2), and the MBSTF-to-MB-UPF hand-off at Nmb9 is defined in TS 23.247 (TS 23.247 V20.0.0 clause 5.3.1); TS 26.517 also specifies the FLUTE/ALC object carriage, the packet distribution format and the JSON/YAML schema for the User Service Announcement (TS 26.517 V19.3.0 clause 6.2, 7, A.2.1). This split (service-based APIs on the control plane, defined protocols on the user plane) mirrors the figure above and is the same pattern used throughout the 5G Core.

## Implementation blueprint

The provisioning-to-announcement flow from "Session life-cycle and announcement" above, as a step-by-step reference. See the [Implementation Blueprints index](/tech/blueprints) for the other blueprints on this portal.

| Step | Reference point | What happens | Clause |
| --- | --- | --- | --- |
| 1. Provision MBS Services | Nmb1 | Ahead of activation, the MBSF provisions the low-level MBS Services the ingest session needs on the MB-SMF | TS 26.502 V19.6.0 clause 4.5.2 step 4, 5.3 |
| 2. Configure Distribution Sessions | Nmb2 | The MBSF configures the corresponding MBS Distribution Sessions on the MBSTF | TS 26.502 V19.6.0 clause 4.5.2 step 5, 5.3 |
| 3. Ingest begins | Nmb8 | The AF/AS ingests content into the MBSTF, using the object (FLUTE/ALC) or packet distribution method as provisioned | TS 26.502 V19.6.0 clause 6.1, 6.2; TS 26.517 V19.3.0 clause 6.2, 8.2 |
| 4. Build the announcement | n/a | The MBSF compiles one MBS Distribution Session Announcement per distribution session and bundles them into an MBS User Service Announcement | TS 26.502 V19.6.0 clause 4.5.2 step 6, 4.5.7; TS 26.517 V19.3.0 clause A.2.1 |
| 5. Expose the announcement | MBS-5 / MBS-4-MC | A client retrieves it by unicast pull (MBS-5) or by listening to a carousel, in-band or in a dedicated announcement session (MBS-4-MC) | TS 26.502 V19.6.0 clause 4.2.4, 5.4 |
| 6. Teardown | n/a | When the ingest session deactivates, the MBSF deactivates the Distribution Sessions and tears down (or, for a multicast service with further active periods, deactivates) the MBS Sessions it provisioned in steps 1 and 2 | TS 26.502 V19.6.0 clause 5.5.4 |
