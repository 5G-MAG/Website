FLUTE feature by feature in its three profiles: what each one requires, permits or excludes. The [Standards page](/standards/content-delivery/flute) lists the clauses behind every requirement.

Each profile takes FLUTE from a different set of documents, and the columns follow them:

- **Unprofiled FLUTE:** the IETF documents (RFC 3926 section 1; TS 26.346 V19.3.0 clause 7.1). Version 1 (RFC 3926, with ALC and LCT) unless version 2 is named.
- **MBMS download:** RFC 3926 with the ALC and LCT features FLUTE inherits, TS 26.346 clause 7.2, the session description of clause 7.3, the MBMS Download Profile of annex L.4 and the requirement levels of annex A.
- **MBS Object Distribution:** the MBMS Download Profile of annex L.4, the Profiled FDT Schema of annex L.6, the session description of TS 26.346 clause 7.3 with the restrictions of TS 26.517, and TS 26.517 clause 6.2. TS 26.346 clause 7.2 binds it only where annex L.4 repeats it.

:::tip[At a glance]

- **What it covers:** how unprofiled FLUTE, MBMS download and MBS Object Distribution differ in what they require.
- **Unprofiled FLUTE** leaves most choices open; the MBMS and MBS profiles narrow it for a network without congestion control.
- **Releases:** Release 19 raises both FDT schema versions and adds repair features; Release 18 changes only wording.

:::

## Sessions, objects and packets

<details>
<summary>Unprofiled FLUTE</summary>

- A Transport Session Identifier (TSI) is associated with each session and carried in the LCT header of each ALC packet (RFC 3450 section 2.1; RFC 3450 section 4.4). The pair of sender IP address and TSI uniquely identifies the session, and the sender uses the same TSI for all packets of the session.
- A receiver joined to several sessions demultiplexes on the IP address of the sender and the TSI (RFC 3450 section 1.3; RFC 3450 section 4.5). It verifies each packet's header, sender address and TSI, and discards a packet that does not match a session it has joined.
- Each file is associated with a Transport Object Identifier (TOI) greater than 0; the TOI is carried in the packets of the session (a payload-free packet that closes the session does not carry it); TOI 0 is reserved for the FDT Instances (RFC 3926 section 3.1).
- Before joining, a receiver obtains the session description; a receiver that cannot process the ALC header drops from the session, and one that cannot implement the congestion control of the session does not join (RFC 3450 section 2.4; RFC 3450 section 4.5).

</details>

<details>
<summary>MBMS download</summary>

- The TSI is 16 bits long (S=0, H=1) and the TOI should be 16 bits long (O=0, H=1) (TS 26.346 V19.3.0 clause 7.2.7).
- A session has exactly one sender IP address, given by one `source-filter` attribute at session level; each TSI identifies its session for that source address while it is active, and long before and after (TS 26.346 V19.3.0 clause 7.3.2.1; TS 26.346 V19.3.0 clause 7.3.2.4).

</details>

<details>
<summary>MBS Object Distribution</summary>

- The session description of TS 26.346 clause 7.3 applies, so a session has exactly one source address and one TSI. The 16-bit field lengths of clause 7.2.7 are not repeated in the MBMS Download Profile.

</details>

## LCT header and extensions

<details>
<summary>Unprofiled FLUTE</summary>

- The default LCT header of RFC 3451 is used; reserved bits are set to zero by the sender and ignored by the receiver (RFC 3450 section 4.1; RFC 3451 section 5.1).
- The sender may set the Close Session (A) and Close Object (B) flags as the end of the session or of an object approaches; a receiver should then assume no more packets follow (RFC 3451 section 5.1).
- Every packet of an FDT Instance carries the FDT Instance Header (EXT_FDT) (RFC 3926 section 3.4; RFC 3451 section 5.2). All implementations support EXT_NOP and recognise EXT_AUTH.

</details>

<details>
<summary>MBMS download</summary>

- **Header fields:** a 32-bit CCI with value zero (C=0), a 16-bit TSI, a TOI that should be 16 bits, TOI 0 used only for FDT Instances, and HDR_LEN giving the header length in 32-bit words (TS 26.346 V19.3.0 clause 7.2.7).
- **Flags:** the Close Session (A) and Close Object (B) flags may signal the end of a session and of an object; the Sender Current Time (T) and Expected Residual Time (R) flags are set to zero (TS 26.346 V19.3.0 clause 7.2.7; TS 26.346 V19.3.0 clause A). EXT_TIME, if included, carries the Expected Residual Time. Annex A sets the levels for client and server, with a note on the A flag.
- **Extensions:** EXT_FTI in every packet carrying an FDT Instance and never in packets carrying files; EXT_CENC is not used (TS 26.346 V19.3.0 clause 7.2.8).

</details>

<details>
<summary>MBS Object Distribution</summary>

- The MBMS Download Profile does not use the Sender Current Time and Expected Residual Time, either as the T and R flags or in EXT_TIME: the network should set them to zero and the UE should ignore them (TS 26.346 V19.3.0 clause L.4.7).
- EXT_FTI should be used in packets carrying FDT Instances; the FEC Object Transmission Information of files should be conveyed in the FDT (TS 26.346 V19.3.0 clause L.4.7).

</details>

## The File Delivery Table

<details>
<summary>Unprofiled FLUTE</summary>

- The FDT is local to its file delivery session, and provides a file description entry mapped to a TOI for each file in the session (RFC 3926 section 3.2).
- The FDT-Instance element contains the Expires attribute (RFC 3926 section 3.4.2). Each File element contains at least the TOI and Content-Location attributes. Content-Type, Content-Length, Content-Encoding and Content-MD5 are used as HTTP/1.1 defines them, where present.
- A TOI may be described more than once, but later FDT Instances do not change the parameters already described for it (RFC 3926 section 3.3). The sender uses an expiry time in the future; the receiver should not use an FDT Instance after it expires.

</details>

<details>
<summary>MBMS download</summary>

- **Schema:** the extended FLUTE FDT instance schema of TS 26.346 clause 7.2.10.1, based on the RFC 3926 schema, with its schemaVersion element; it imports the 3GPP extensions of Releases 6, 7, 8, 9, 11, 13 and, from Release 19, 19.
- **Mandatory beyond RFC 3926:** Content-Length, Content-Type, the FEC Encoding ID, and the FEC Object Transmission Information of the FEC scheme in use (TS 26.346 V19.3.0 clause 7.2.9). With Compact No-Code FEC, the maximum source block length does not exceed 65535.
- **Optional:** Complete, Content-Encoding, Content-MD5 (indicated when several versions of a file are expected), IndependentUnitPositions, File-ETag, and, from Release 19, Repair-Start and Repair-Limit-Percentage (TS 26.346 V19.3.0 clause 7.2.9).
- **3GPP extensions:** file grouping (clause 7.2.6), the MBMS session identity of a file (7.2.11), caching directives (7.2.13), FullFDT for a full snapshot of the objects scheduled (7.2.14), the decryption key of a protected file (7.2.15), and the FEC redundancy level of a file (7.2.16) (TS 26.346 V19.3.0 clause 7.2.6; TS 26.346 V19.3.0 clause 7.2.11; TS 26.346 V19.3.0 clause 7.2.13; TS 26.346 V19.3.0 clause 7.2.14; TS 26.346 V19.3.0 clause 7.2.15; TS 26.346 V19.3.0 clause 7.2.16).
- **Expiry:** the UE shall not use an FDT Instance to interpret packets received after it expires, which strengthens the RFC 3926 "should not". (TS 26.346 V19.3.0 clause 7.2.9)
- **The MBMS Download Profile** (annex L.4) constrains this set, as in the next column (TS 26.346 V19.3.0 clause L.4.1).

</details>

<details>
<summary>MBS Object Distribution</summary>

- **The MBMS Download Profile:** the sender carries Content-Type and the FEC Object Transmission Information at the FDT-Instance or File level, and Content-Location, TOI and Content-Length for every file; Content-MD5 should be included for non-DASH services and may be for DASH Segments (TS 26.346 V19.3.0 clause L.4.2; TS 26.346 V19.3.0 clause L.4.3; TS 26.346 V19.3.0 clause L.4.4). It does not use a Content-Encoding other than gzip, FEC-OTI-FEC-Instance-ID, Group, Complete, FullFDT, MBMS-Session-Identity-Expiry, Transfer-Length, Decryption-KEY-URI, FEC-Redundancy-Level or MBMS-Session-Identity. The receiver supports every attribute the sender carries.
- **The Profiled FDT Schema** (annex L.6) describes the objects currently transmitted, with its own schemaVersion; delimiter elements are set to 0 and ignored (TS 26.517 V19.3.0 clause 6.2.1; TS 26.346 V19.3.0 clause L.6.2; TS 26.346 V19.3.0 clause L.6.3).
- **TS 26.517:** objects are described with Expires; Content-MD5 and File-ETag are optional, File-ETag carrying the HTTP entity tag. In OBJECT_STREAMING mode, each Content-Location matches the object's URL in the object list, File@Expires is no later than its latest availability start time, and Cache-Control@Expires gives its availability end time.

</details>

## FEC and blocking

<details>
<summary>Unprofiled FLUTE</summary>

- Every packet carries an FEC Payload ID, which the receiver uses to place the encoding symbols it carries (RFC 3450 section 2.3).
- The FEC Object Transmission Information is delivered in band (RFC 3926 section 5). The receiver supports it in EXT_FTI for FDT Instances, and both in EXT_FTI and in the FDT for files; the two carry the same values.
- Compact No-Code (FEC Encoding ID 0, RFC 3695) is required at the client and the default at the server; other FEC schemes, such as Raptor (RFC 5053) and RaptorQ (RFC 6330), are optional (TS 26.346 V19.3.0 clause A; RFC 3926 section 5.1.2.3). The RFC 3926 blocking algorithm is recommended.

</details>

<details>
<summary>MBMS download</summary>

- Compact No-Code shall be supported, with a 16-bit Source Block Number and a 16-bit Encoding Symbol ID in the FEC Payload ID (TS 26.346 V19.3.0 clause 7.2.2; TS 26.346 V19.3.0 clause 7.2.7).
- A UE that supports MBMS User Services supports a decoder for the Raptor FEC scheme (FEC Encoding ID 1, the MBMS FEC scheme of clause 7.2.12); given a mathematically sufficient set of encoding symbols, it recovers the entire source block (TS 26.346 V19.3.0 clause 7.2.2; TS 26.346 V19.3.0 clause 7.2.12.1).
- Blocking: the RFC 3926 algorithm with Compact No-Code, the RFC 5053 algorithm with Raptor; the sub-block size stays below 256 KB (TS 26.346 V19.3.0 clause 7.2.3).
- The FEC-Redundancy-Level of a transport object may be given in the FDT (clause 7.2.16) (TS 26.346 V19.3.0 clause 7.2.16).

</details>

<details>
<summary>MBS Object Distribution</summary>

- In the MBMS Download Profile, Compact No-Code and Raptor are optional to implement by the sender and mandatory to support by the UE. Blocking follows the algorithm of RFC 3926 for Compact No-Code (TS 26.346 clause 7.2.3) and the parameter recommendations of RFC 5053 for Raptor (TS 26.346 V19.3.0 clause L.4.7; RFC 5053 section 4.2). Blocking should follow RFC 3695 for Compact No-Code and the parameter recommendations of RFC 5053 for Raptor.
- The repair procedures handle both schemes: with Compact No-Code the MBS Client considers the source symbols already received, with Raptor the source and repair symbols already received (TS 26.517 V19.3.0 clause 6.2.4.5).

</details>

## Congestion control and channels

<details>
<summary>Unprofiled FLUTE</summary>

- Implementors of ALC implement a multiple-rate, feedback-free congestion control building block in accordance with RFC 2357, applied to all packets of a session (RFC 3450 section 2.2). In FLUTE version 2, implementations of ALC support at least WEBRC (RFC 3738), a multiple-rate congestion control scheme (RFC 6726 section 1.1.4).
- RFC 3926 allows a single channel, or multiple channels, without the congestion control of ALC only in a controlled network where flow and congestion control are provided by other means (RFC 3926 section 4).

</details>

<details>
<summary>MBMS download and MBS Object Distribution</summary>

- Congestion control is not appropriate in the environment MBMS download is provided in, and is not used (TS 26.346 V19.3.0 clause 7.1; RFC 3450 section 1.3).
- FLUTE channelization is a single FLUTE channel with single rate transport (clause 7.2.4 for MBMS download, clause L.4.7 for both) (TS 26.346 V19.3.0 clause 7.2.4; TS 26.346 V19.3.0 clause L.4.7).

</details>

## Content encoding

<details>
<summary>Unprofiled FLUTE</summary>

- FDT Instances and other files may be content encoded (RFC 3926 section 3.4.3; RFC 3926 section 3.4.2). EXT_CENC signals the encoding of an FDT Instance, in every packet of that instance.

</details>

<details>
<summary>MBMS download</summary>

- Files may be gzip encoded for transport, and UEs support gzip decoding (TS 26.346 V19.3.0 clause 7.2.5; TS 26.346 V19.3.0 clause 7.2.8). FDT Instances are not content encoded, so EXT_CENC is not used.

</details>

<details>
<summary>MBS Object Distribution</summary>

- Content-Encoding set to gzip may be carried and is supported by the receiver; any other Content-Encoding is excluded (TS 26.346 V19.3.0 clause L.4.2).
- The repair object of a gzip-encoded object is hosted on the MBS AS in its gzip form, with a ".gz" extension added to its location (TS 26.517 V19.3.0 clause 6.2.4.4).

</details>

## Session description

<details>
<summary>Unprofiled FLUTE</summary>

- RFC 3926 lists what a receiver needs before joining: the source IP address, the number of channels, the destination address and port of each channel, the TSI and an indication that the session is a FLUTE session; optionally, the start and end times of the session (RFC 3926 section 6). How the receiver discovers them is out of its scope.

</details>

<details>
<summary>MBMS download</summary>

- An SDP file describes the session (TS 26.346 clause 7.3): the source filter, the channel, the TSI, the timing, the MBMS bearer mode and TMGI, the FEC capabilities, the bandwidth, `FLUTE/UDP` as protocol and `application` media with format `0`.
- Table L.4.8-1 of the MBMS Download Profile lists which SDP parameters are required, optional or not applicable (TS 26.346 V19.3.0 clause L.4.8; TS 26.346 V19.3.0 clause L.4.1). The profile excludes OMA Push and RTSP.

</details>

<details>
<summary>MBS Object Distribution</summary>

- The Session Description document follows TS 26.346 clause 7.3 with restrictions: no mode of MBMS bearer per media, no QoE metrics, no service language and no alternative TMGI. Its timing covers the service schedule descriptions, if any.
- The `mbs-servicetype` attribute declares whether the MBS Distribution Session uses a broadcast or a multicast MBS Session, with the TMGI, for example `a=mbs-servicetype:broadcast 123869108302929` (TS 26.517 V19.3.0 clause 6.2.2.2).

</details>

## Reception and operating modes

<details>
<summary>MBMS download</summary>

- A UE application instructs the FLUTE receiver to receive every file available (promiscuous), one copy of specific files (one-copy), or specific files and every update to them (keep-updated) (TS 26.346 V19.3.0 clause 7.2.0).

</details>

<details>
<summary>MBS Object Distribution</summary>

- **OBJECT_SINGLE:** a single object (TS 26.517 V19.3.0 clause 6.2.3.2).
- **OBJECT_COLLECTION:** several objects listed in an object manifest, each distributed once (TS 26.517 V19.3.0 clause 6.2.3.3). Each FDT Instance should describe all objects of the collection.
- **OBJECT_CAROUSEL:** one or more objects from an object manifest, distributed repeatedly; the manifest may be replaced over time (TS 26.517 V19.3.0 clause 6.2.3.4).
- **OBJECT_STREAMING:** a sequence of objects, typically timed segments, recommended for DASH or HLS (TS 26.517 V19.3.0 clause 6.2.3.5). The last packet of each object reaches the MBSTF Client by its availability start time, and an FDT Instance describing the objects not yet fully transmitted should be sent frequently.

</details>

## Caching directives

<details>
<summary>MBMS download</summary>

- A file download service may indicate, per file, whether it is not to be cached (no-cache), cached for an indefinite period if possible (max-stale), or cached until a given time (Expires) (TS 26.346 V19.3.0 clause 7.2.13). The directives are recommended with the promiscuous and keep-updated modes.

</details>

<details>
<summary>MBS Object Distribution</summary>

- The MBMS Download Profile lets the sender carry the Cache-Control element, and the receiver supports it (TS 26.346 V19.3.0 clause L.4.4; TS 26.346 V19.3.0 clause L.6.1; TS 26.346 V19.3.0 clause L.6.2). The Profiled FDT Schema declares Cache-Control, with the same three directives, in its own namespace.
- In OBJECT_STREAMING mode, Cache-Control@Expires gives the availability end time of each object (TS 26.517 V19.3.0 clause 6.2.3.5).

</details>

## Repair

<details>
<summary>MBMS download</summary>

- **Post-delivery file repair** (TS 26.346 clause 9.3): MBMS Download receivers support it. It repairs lost or corrupted file fragments, and spreads the repair requests in time and across servers. Reception reporting follows in clause 9.4.
- **In-session unicast file repair** (TS 26.346 V19.3.0 clause 9.4B, Release 19): MBMS Download receivers support it if the UE permits concurrent use of MBMS bearer services and unicast reception. Its procedures are those of TS 26.517 clause 6.2.4.3.

</details>

<details>
<summary>MBS Object Distribution</summary>

- **Post-session Object Repair:** the MBS Client supports it. It is aligned with the file repair of TS 26.346 clause 9.3, and uses byte-range requests to the MBS AS.
- **In-session object repair** (Release 19; for further study in Release 18): the object delivery client requests missing data, or the whole object, over HTTP from the object repair server once a repair start time is reached, within a limit of repairs per 100 objects (TS 26.517 V19.3.0 clause 6.2.4.3.3; TS 26.517 V19.3.0 clause 6.2.4.3.2).
- **Not with OBJECT_STREAMING:** the Object Repair mechanism is not used with the OBJECT_STREAMING mode in this release (TS 26.517 V19.3.0 clause 6.2.3.1).

</details>

## Security

<details>
<summary>Unprofiled FLUTE</summary>

- The RFCs recommend an integrity check of each reconstructed object and FDT Instance, packet-level authentication, and measures that keep receivers from accepting an incorrect session description (RFC 3926 section 7; RFC 3450 section 5). The FLUTE receiver should not have write access to system files.

</details>

<details>
<summary>MBMS download and MBS Object Distribution</summary>

- A protected download file can name its decryption key file with the Decryption-KEY-URI attribute (TS 26.346 clause 7.2.15). The MBMS Download Profile excludes that attribute from the FDT the sender carries.

</details>

## FLUTE version 2

RFC 6726 changes some of these rules for version 2, which the 3GPP profiles do not use: (RFC 6726 section 11.1; TS 26.346 V19.3.0 clause 7.1)

- The receiver **must not** use an FDT Instance after it expires (version 1: should not) (RFC 6726 section 3.3; RFC 3926 section 3.3).
- When the FEC Object Transmission Information is delivered in the FDT, the FEC-OTI-FEC-Encoding-ID attribute and the Codepoint field of all packets for that TOI must have the same value (RFC 6726 section 5).
- Senders do not reuse the ID of an FDT Instance that has not expired, and receivers handle FDT Instance ID wraparound (RFC 6726 section 3.4.1).
- Content-Type should be included, and Content-Encoding is included whenever content encoding is applied (RFC 6726 section 3.4.2).
- Version 2 uses ALC (RFC 5775) and LCT (RFC 5651), whose header differs from version 1 (RFC 6726 section 3.1; RFC 6726 section 11.1).
