## Description

With the "Connectivity Insights" API, developers gain visibility into network quality: they can check whether their application's network requirements can be met for a given user session. Based on the API's response, developers can make informed decisions, such as requesting a network boost through the CAMARA Quality on Demand API or adjusting application settings (e.g., video resolution) to ensure the best possible user experience (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml info.description Introduction).

This API performs a single, on-demand ("one-shot") check. For continuous monitoring that pushes an event notification whenever network quality changes, see the companion [Connectivity Insights Subscriptions API](/tech/network-apis/features/connectivity-insights-subscriptions) (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml info.description API functionality; CAMARA ConnectivityInsights main@db9c0de connectivity-insights-subscriptions.yaml `/subscriptions` POST callbacks notifications).

Information: [Connectivity Insights project page](https://camaraproject.org/connectivity-insights/) and [GitHub repository](https://github.com/camaraproject/ConnectivityInsights)

The API definitions can be obtained here: [ConnectivityInsights API_definitions folder](https://github.com/camaraproject/ConnectivityInsights/tree/main/code/API_definitions)

The Connectivity Insights API definition (YAML) is available at: [connectivity-insights.yaml](https://github.com/camaraproject/ConnectivityInsights/blob/main/code/API_definitions/connectivity-insights.yaml)

## Operations and dependencies

### Connectivity Insights API

- **POST /check-network-quality** with the request body containing an `applicationProfileId`, an `applicationServer` (IPv4 and/or IPv6 address) and, optionally, `applicationServerPorts`, `device` (required with a two-legged access token) and `monitoringTimeStamp` - Check the network quality. Response shows the network's current level of confidence (qualitative) that it can meet an application profile's quality thresholds (according to those defined in the `applicationProfileId`) for a given end user device.
  - Dependency: Requires `applicationProfileId` from a previous call to the [**Application Profiles API**](/tech/network-apis/features/application-profiles) (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml NetworkQualityInsightRequest required applicationProfileId; info.description step 1; `/check-network-quality` POST 404).

## Standardisation context

Connectivity Insights is defined in OpenAPI 3.0.3; the held definition is a work-in-progress version (`version: wip`) that declares `x-camara-commonalities: 0.9.0` (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml info). It is a read-only, request/response API: it does not change any network state and does not create a QoS session. In the 3GPP northbound model a QoS request corresponds to the NEF `AsSessionWithQoS` operation ([TS 29.522](https://www.3gpp.org/dynareport/29522.htm) V20.1.0 clause 4.4.9.2.0). A Connectivity Insights provider may instead use sources such as the monitoring events (TS 29.522 V20.1.0 clause 4.4.2) and the analytics information (clause 4.4.14.1) that the NEF exposes. The CAMARA definition names no particular source; an operator may satisfy the check from live measurements, from analytics, or from a mix.

The design decision most relevant to media is the qualitative response. Each threshold field in the reply carries a string such as `"meets the application requirements"` rather than a measured value; `additionalKPIs` adds supporting context (for example `signalStrength`, `connectivityType`). This keeps the API operator-agnostic (operators do not have to expose raw core measurements), but it limits how much an application can adapt: it learns that a requirement is not met, but not by how much. 5G-MAG's Self-Assessment records this as a gap for professional media, where a quantitative figure (for example the actual latency on the device-to-application-server path) would allow targeted remedies.

By default the check uses the current date and time; the optional `monitoringTimeStamp` can carry a future date and time for predictive data. For a scheduled production, a passing check does not guarantee the resource will still be available when the event starts. Where advance assurance is needed, a reservation-style API ([QoS Booking](/tech/network-apis/features/qos-booking) or [Network Slice Booking](/tech/network-apis/features/network-slice-booking)) is more appropriate, and where a boost is needed at the moment, [Quality on Demand](/tech/network-apis/features/quality-on-demand) actually requests QoS rather than merely reporting on it. Connectivity Insights is therefore best read as a decision input, not a guarantee (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml NetworkQualityInsightRequest.monitoringTimeStamp; CAMARA QualityOnDemand main@471aa35 quality-on-demand.yaml tags/info; CAMARA QoSBooking main@4de93f1 qos-booking.yaml info.description).

### Step 0: Pre-conditions

- Create an application profile using the **Application Profiles API** (with the relevant application requirements) (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml info.description API functionality usage step 1).
- Create a device object for the device which media flow is to be monitored (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml NetworkQualityInsightRequest.device; info.description identifying the device from the access token).
- Obtain IP address and port of the application server (Ingest Server of Production).

### Step 1: Obtain one-shot information on network quality

- **POST /check-network-quality**, passing the **applicationProfileId** obtained in step 0, the address/port of an application server, and a device object (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml info.description usage step 2; NetworkQualityInsightRequest).

## 5G-MAG's Self-Assessment

This section records 5G-MAG's practical reading of the API and the open points it raises for media use.

The APIs are likely to be invoked to obtain information about the ability of the network to meet the requirements either before or during operation. However:

- By default the information received reflects the current date and time. The optional `monitoringTimeStamp` can request predictive data for a future time, but the response carries no indication of how reliable that prediction is for the actual time in which the network should be used (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml NetworkQualityInsightRequest.monitoringTimeStamp; NetworkQualityInsightResponse).
- The information received is qualitative (e.g. `"targetMinDownstreamRate": "meets the application requirements"`). An application would be unable to understand which parameters to be adapted in order to revert a situation in which requirements cannot be met.

Potential improvements:

- If used to monitor resources for which QoS was requested (via a different API) harmonisation of Application Profile and QoS Profile for consistency.
- an indication of the actual performance parameters (quantitative) for those defined in the Application Profile may provide better insight for potential remedies. E.g. latency cannot be fulfilled, but please respond with the actual latency the link device-AS is experiencing.

## Connectivity Insights API Usage

### Obtain information about network quality

With **POST /check-network-quality** passing (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml `/check-network-quality` POST):

- the **ApplicationProfileId**, (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml NetworkQualityInsightRequest.applicationProfileId)
- the device object (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml NetworkQualityInsightRequest.device)
- identifier for the application server (IPv4 and/or IPv6 address and ports) (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml NetworkQualityInsightRequest.applicationServer, applicationServerPorts; ApplicationServer)

```json
{
  "applicationProfileId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "device": {
    "phoneNumber": "+123456789",
    "ipv4Address": {
      "publicAddress": "203.0.113.0",
      "publicPort": 59765
    },
    "ipv6Address": "2001:db8:85a3:8d3:1319:8a2e:370:7344"
  },
  "applicationServer": {
    "ipv4Address": "192.168.0.1/24",
    "ipv6Address": "2001:db8:85a3:8d3:1319:8a2e:370:7344"
  },
  "applicationServerPorts": {
    "ranges": [
      {
        "from": 5010,
        "to": 5020
      }
    ],
    "ports": [5060, 5070]
  },
  "monitoringTimeStamp": "2023-07-03T12:27:08.312Z"
}
```

Type of response: The network's current level of confidence that it can meet an application profile's quality thresholds for a given end user device. Each threshold field carries a qualitative string (for example `"meets the application requirements"`) rather than a measured value; `additionalKPIs` gives supporting signal information. The exact set of allowed strings is defined in the [connectivity-insights.yaml](https://github.com/camaraproject/ConnectivityInsights/blob/main/code/API_definitions/connectivity-insights.yaml) (CAMARA ConnectivityInsights main@db9c0de connectivity-insights.yaml `/check-network-quality` POST description; NetworkQualityThresholdsConfidence; AdditionalKpis).

```json
{
  "packetDelayBudget": "meets the application requirements",
  "targetMinDownstreamRate": "meets the application requirements",
  "targetMinUpstreamRate": "meets the application requirements",
  "packetlossErrorRate": "meets the application requirements",
  "jitter": "meets the application requirements",
  "additionalKPIs": {
    "signalStrength": "excellent",
    "connectivityType": "5G-SA"
  }
}
```
