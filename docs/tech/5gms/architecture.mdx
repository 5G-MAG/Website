<span class="topic-banner__kicker">5G Media Streaming (5GMS)</span>
<h1>Architecture</h1>
</div>
</div>

TS 26.501 describes 5GMS in two ways. The **5GMS architecture**, defined since Release 16, names the functions and reference points of media streaming in downlink and uplink. Since Release 18 it also defines a **generalised Media Delivery architecture**, shared with Real-Time media Communication (RTC), of which 5GMS is one realisation. Where the two disagree, the 5GMS architecture takes precedence.

:::tip[At a glance]

- **Reference points:** M1 to M8, in downlink (M1d to M8d) and uplink (M1u to M8u). Release 19 adds M10 and M13 in both directions.
- **Where the APIs are specified:** in TS 26.512 up to Release 17. From Release 18, provisioning and media session handling are TS 26.510 services, which TS 26.512 refers to.
- **Generalisation:** first in TS 26.501 version 18.5.0 (March 2024). The 5GMS AF and AS are realisations of the general Media AF and Media AS.
- **For developers:** the clause for each reference point, release by release, is under Where each reference point is specified.

:::

- **5GMS Application Provider:** uses 5GMS for its streaming services, and provides a 5GMS-Aware Application on the User Equipment (UE).
- **5GMS AF:** an Application Function dedicated to 5G Media Streaming. It provides control functions to the Media Session Handler on the UE and to the Application Provider. It may relay or initiate a request for Policy and Charging Function (PCF) treatment, or interact with other network functions through the Network Exposure Function (NEF).
- **5GMS AS:** an Application Server dedicated to 5G Media Streaming.
- **5GMS Client:** a function inside the UE dedicated to 5G Media Streaming, made of a Media Session Handler and a Media Player (downlink) or Media Streamer (uplink). A UE may also be implemented in a self-contained manner, so that reference points M6 and M7 are not exposed at all.
- **5GMS-Aware Application:** the application on the UE that uses the 5GMS Client and network functions through 5GMS interfaces and APIs.

The AF and AS are data network functions and reach the UE over N6. An AF in the operator's trusted data network may communicate directly with the relevant 5G Core functions. One in an external data network may only reach them through the NEF, over N33.

### Downlink (5GMSd)

In downlink the network is the origin of the media. The content hosting feature provides a service equivalent to a CDN, inside or outside the trusted data network. The 5GMSd AS functions listed in TS 26.501 include content ingest at M2d, caching, content preparation, and, at M4d, geographic restrictions on content access and URL signing.

| **M3d** | 5GMSd AS Configuration and Management API | AS | AF | Configure and manage the AS |
| **M4d** | 5GMSd Media Streaming interface | Between the AS and the Media Player | | Stream media in real time, or download it |
| **M5d** | 5GMSd Media Session Handling API | AF | Media Session Handler | Session handling, control, reporting and assistance, with authorisation and authentication |
| **M6d** | 5GMSd Media Session Handling Client API | Media Session Handler | Application; Media Stream Handler (at M11d) | Use of 5GMS functions |
| **M7d** | 5GMSd Media Access Client API | Media Player | Application; Media Stream Handler at M11d, as TS 26.501 clause 4.2.1 words it (clause 4.1.2.5.2 names the Media Session Handler) | Media access control |

In TS 26.501 V19.4.0 (clause 4.2.2), the Media Session Handler subfunctions include Dynamic Policy, Network Assistance, Service URL Handling, and In-band client data reporting configuration.

### Uplink (5GMSu)

In uplink the UE is the origin of the media and the network consumes it. The roles mirror downlink, with a "u" suffix:

- The **5GMSu Application Provider** receives the media, for example for storage, consumption, transcoding and redistribution.
- The **5GMSu AS** receives the media from the UE.
- The **5GMSu Client** holds a **Media Streamer** in place of the Media Player. It streams the media to the AS, and serves both the application and the Media Session Handler.

| **M3u** | 5GMSu AS Configuration and Management API | AS | AF (see note) | Configure and manage the AS |
| **M4u** | 5GMSu Media Streaming interface | Between the Media Streamer and the AS | | Contribute uplink media |
| **M5u** | 5GMSu Media Session Handling API | AF | Media Session Handler | Session handling, control and assistance, and QoE metrics reporting |
| **M6u** | 5GMSu Media Session Handling Client API | Media Session Handler | Application; Media Session Handler (as TS 26.501 words it) | Use of 5GMSu functions |
| **M7u** | 5GMSu Media Access Client API | Media Streamer | Application; Media Session Handler | Media access, including configuration and collection of QoE metrics |

Release 19 also adds M10u and M13u to the uplink mapping (TS 26.501 V19.4.0 table 4.1.2.4-1).

Note on M3u: TS 26.501 V19.4.0 clause 4.3.1 reads "exposed by the 5GMSu AS to the 5GMSu AS"; its generalised architecture (clause 4.1.2.5.2) has the Media AF using M3 to configure the Media AS.

## Before and after generalisation

The generalised architecture first appears in TS 26.501 version 18.5.0 (March 2024), through a change titled "5GMS Functions are general Media Functions". TS 26.501 gives the reason: 5GMS and RTC functions may share many common functionalities for media session handling and media delivery. The 5GMS AF is one possible realisation of the general Media AF, and the 5GMS AS of the general Media AS. Full integration of 5GMS and RTC is not addressed in TS 26.501.

| | Release 16 | Release 17 | Release 18 | Release 19 |
| --- | --- | --- | --- | --- |
| **Generalised Media Delivery architecture** | No | No | Yes, from V18.5.0 | Yes |
| **Reference points** | M1 to M8 | M1 to M8 | M1 to M8, and M9 to M12 | M1 to M8, and M9 to M13 |
| **M3 (AF and AS)** | Internal and not specified | Internal and not specified | An API used by the AF to configure and manage the AS, from TS 26.501 V18.2.0 | An API exposed by the AS to the AF |
| **Provisioning and session APIs** | TS 26.512 | TS 26.512 | TS 26.510 (created in Release 18), referred to by TS 26.512 | TS 26.510, referred to by TS 26.512 |

## How a downlink session runs

TS 26.501 clause 5.2.3 specifies the procedure for DASH streaming in 19 steps. Condensed, with the step numbers:

**Before the session:** the Application Provider has provisioned the 5GMS System and set up content ingest, and the application has received the service announcement. Provisioning starts with a Provisioning Session at M1d (TS 26.512 clause 4.3.2.1).

1. **Discovery (steps 1 and 2).** The application runs service announcement and content discovery, and a media content item is selected.
2. **Start (step 3).** The application triggers the 5GMSd Client to start playback and gives it the Media Player Entry.
3. **Service Access Information (step 4, M5d).** If the application received only a reference, the Media Session Handler acquires the whole Service Access Information from the AF.
4. **Manifest (steps 5 to 10, M4d).** The Media Player requests, receives and processes the MPD, and notifies the Media Session Handler.
5. **Preparation (steps 11 to 14).** Optionally the Media Player acquires DRM information. It configures the playback pipeline, establishes the transport sessions, and tells the Media Session Handler it is ready.
6. **Playback (steps 15 to 19, M4d).** The Media Player requests initialisation information and media segments according to the MPD, and repeats this as the MPD directs.

During a session the Media Session Handler also provides dynamic policy, network assistance, and consumption and metrics reporting (TS 26.501 clause 4.2.2).
